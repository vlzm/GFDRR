# План создания канонической документации

> Этот файл — рабочий план. Он написан, чтобы начать работу в новом чате без
> прежнего контекста: здесь есть цель, целевой состав документов, уже принятые
> решения и пошаговый порядок работы. После выполнения последнего шага этот
> файл удаляется.

## Цель

Собрать в `docs/` минимальный, но полный набор документов, чтобы новый человек
(или сам автор через полгода) быстро понял, как устроена вся разработка.

Организующая идея: документ `docs/comprehension_levels.md` (бывший
`docs/уровни_понимания_кода.md`, переведён в шаге 5) описывает пять
уровней понимания кода (от «умею запустить» до «понимаю каждую строчку»).
Набор документации полон, когда каждый уровень закрыт ровно одним артефактом,
и минимален, когда ни один уровень не закрыт двумя.

| Уровень понимания | Артефакт, который его закрывает |
|---|---|
| 1 — умею запустить | секция «Как запустить» в `docs/README.md` |
| 2 — крупные блоки и что они друг другу передают | `docs/README.md` (рассказ + карта репозитория) |
| 3 — все модули и их контракты в общих словах | `docs/simulator.md` и `docs/rebalancing.md` |
| 4a — точные контракты: схемы таблиц, инварианты | `Notations.md` (корень) + `docs/scenarios.md` |
| 4b — почему устроено так, а не иначе | секции «Why it is built this way» внутри `simulator.md` и `rebalancing.md` |
| 5 — построчная реализация | не документ: `notebooks/test_pipeline.ipynb` и ноутбуки понимания; `README.md` указывает на них |

## Решения, которые уже приняты (не пересматривать)

1. `Notations.md` остаётся в корне репозитория. Это словарь проекта; все новые
   документы ссылаются на него при первом упоминании термина и не дублируют
   его содержимое.
2. Входная точка — `docs/README.md`. Это файл-рассказ: только текст и ссылки,
   ни одной таблицы и ни одного числа, которые уже живут в другом файле.
3. Уровень 4b не выносится в отдельный документ. Это короткие секции в конце
   `simulator.md` и `rebalancing.md`: 3–5 несущих решений, для каждого — какая
   была альтернатива и почему её отвергли.
4. Канонический язык документов — английский. Русская версия (`*_ru.md`)
   делается только для файлов, которые автор регулярно перечитывает сам.
   Какие именно — решить в шаге 6.
5. Сценарный документ один. Два старых (`scenario_event_tables.md` и
   `scenario_step_id_tables_ru.md`) заменяются новым, собранным от текущего кода.
6. Каждая игрушечная таблица в сценарном документе воспроизводится кодом
   (тестом), чтобы расхождение документа с кодом ловилось запуском, а не глазами.

## Правила, действующие на каждом шаге

- Правила языка и стиля из `CLAUDE.md`: простой язык, без метафор и жаргона,
  каждое понятие определяется простыми словами при первом появлении.
- Словарь — `Notations.md`. Прежде чем назвать что-либо в документе, взять
  слово оттуда. Если понятия нет — сначала добавить его туда.
- Имена кода (`step_id`, `phase_round`, `finalize_flows`) никогда не
  переводятся и не перефразируются.
- Один факт живёт в одном файле. Остальные файлы ссылаются, а не повторяют.
- Диаграмма фаз рисуется только в утверждённом формате скилла `/phase-diagram`
  (участники — пулы велосипедов; на каждую фазу четыре части:
  Reads / Mechanics / Writes / Invariant). Второй формат не изобретать.

## Шаг 3. Документ про симулятор — `docs/simulator.md`

5. Про детали сценариев не писать — ссылаться на `docs/scenarios.md`.

## Порядок и объём сессий

Шаги идут строго по порядку: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Каждый шаг —
отдельная сессия чата; шаг 2 при необходимости делится на две (поездки /
ребалансировка). В начале каждой сессии дать прочитать этот план и
`Notations.md`.
