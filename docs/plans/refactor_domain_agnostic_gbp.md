# Рефакторинг: domain-agnostic `gbp` + `domains/citybike`

Черновик для обсуждения. Фиксирует цель, целевое дерево репозитория и открытые
вопросы. Сам рефакторинг здесь не выполняется.

## Проблема

Сейчас доменная логика (Citi Bike) размазана по всей библиотеке `gbp`: загрузка
сырых данных, названия колонок, депо и грузовики, а также вся ML-часть
(архитектура моделей, признаки, обучение) лежат внутри `gbp`. Из-за этого `gbp`
нельзя использовать как самостоятельную библиотеку под другую задачу, и границы
между «ядром» и «доменом» нет.

## Цель

Разделить репозиторий на два слоя:

- **`gbp`** — самостоятельная **domain-agnostic** библиотека (ядро). Не знает
  ничего про Citi Bike.
- **`domains/citybike`** — реализация конкретной задачи поверх `gbp`. Здесь
  пользователь готовит данные и модели и подключает их к ядру.

**Правило зависимостей:** стрелка всегда `domains → gbp`. `gbp` никогда не
импортирует `domains`. `frontend`, `api` — тоже просто пользователи ядра,
не обязательные для его работы.

## Целевое дерево

```
gbp/                     # ядро, ничего доменного, domains не импортит
  model/                 # ← ВТОРАЯ половина dataloader_graph:
                         #   demand, supply, OD-matrix, flows.
                         #   Это и есть domain-agnostic модель данных.
  consumers/             # симулятор (как есть)
  postprocessing/
  ml/                    # ТОЛЬКО обслуга: загрузка модели, инференс,
                         #   проверка. Умеет подставить demand из ML-модели
                         #   (boosting / sklearn / pytorch) вместо истории.
                         #   Архитектура + признаки + обучение — УЕХАЛИ в domains.
  registry.py            # dict name→loader; домен сам себя регистрирует
  main.py                # оркестратор: имя домена + параметры →
                         #   зарегистрированный loader → данные →
                         #   симуляция → результаты
  api.py                 # FastAPI: run_scenario, plot_commodity_map,
                         #   plot_resources_map, downloads... вся логика UI тут

domains/
  citybike/
    loaders/             # raw + ПЕРВАЯ (доменная) половина graph-loader.
                         #   Вторая половина уехала в gbp.model.
                         #   (открыто: объединять ли raw+graph в один)
    ml/                  # бОльшая часть нынешнего gbp.ml: архитектура,
                         #   признаки, обучение

frontend/                # переписать текст под agnostic: trucks→resources,
                         #   bikes→commodities
data/                    # как есть (или подпапка citybike/)
docs/                    # отдельная большая задача потом
notebooks/  scripts/  tests/   # tests — пересмотреть объём
```

## Механизм реестра

- Реестр-словарь `name → loader` живёт в `gbp` (`registry.py`).
- Доменный пакет при импорте **сам себя регистрирует** в этом словаре.
- Тот, кто запускает прогон (ноутбук, скрипт, CLI, `app`), импортит нужный
  домен — импорт и выполняет регистрацию.
- `gbp.main.run("citybike", params)` находит домен по имени и запускает прогон.
- `gbp` сам `domains` **не импортит** никогда.

## Открытые вопросы

1. Объединять ли `raw` и `graph` лоадеры в один.
2. `gbp.ml` — удалить полностью или свести к обслуге (инференс, проверка).
3. **Контракт на границе.** «loader возвращает `ResolvedModelData`» против «вторая
   половина уезжает в `gbp.model`»: значит loader отдаёт только **доменную** часть,
   а `gbp` достраивает остальное. Наименование границы надо свести — есть
   противоречие с тем, как её резали раньше (доменный объект назывался
   `DomainData`, граница проходила по flow-журналу).
4. Эргономика импорта домена: две строки (`import domains.citybike`, затем
   `gbp.main.run(...)`) против авто-подтяга по имени.
5. `tests` — сколько тестов реально нужно после рефакторинга.
6. `data/` — общая папка или отдельная подпапка на домен.
