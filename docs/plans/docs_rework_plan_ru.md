# План исправления документации

Этот документ — план работ по документации репозитория. Цель: новый человек
(или сам автор через месяц) открывает `docs/README.md` и за один вечер
получает рабочую картину системы, а за первые десять минут — работающий
запуск. Сейчас это не так, и ниже написано почему и что менять, в каком
порядке.

## Диагноз

Цифры на момент написания плана: в `gbp/` и `app/` около 14 000 строк кода,
в живой документации (без `docs/archive/`) около 7 100 строк текста, с
архивом — почти 13 000. Прозы — половина объёма кода.

Четыре проблемы, по убыванию важности.

1. Документы пересказывают код. `simulator.md` — 747 строк, `scenarios.md` —
   608, `ml.md` — 500. Пересказ кода прозой устаревает при каждом изменении,
   удваивает чтение и не заменяет чтение самого кода. Проза должна нести
   только то, что код сказать не может: зачем построено, какие инварианты
   держатся, какая карта у целого.
2. Маршрут читателя перевёрнут. Вход (`docs/README.md`) сначала требует
   понять методику пяти уровней понимания, потом предлагает семь больших
   документов, словарь и ноутбуки. Самый понятный материал — игрушечные
   сценарии из `scenarios.md` (один велосипед, одна станция, несколько строк
   журнала потоков) — показан в конце маршрута, хотя начинать надо с него.
3. Первый запуск не подготовлен. Документация предлагает
   `python app/runner.py`, но исходные CSV не хранятся в git, а папка
   `data/raw/` весит около 9 ГБ. Шага «где взять данные» в основном маршруте
   нет. При этом в `tests/scenarios.py` уже есть синтетические сценарии
   (`single_trip`, `overflow`, `stockout`), которые запускают настоящий
   `Environment` без внешних данных за миллисекунды.
4. Источники истины противоречат друг другу. `CLAUDE.md` говорит: фаза —
   прогноз спроса, канонический сценарий — два запуска. `AGENTS.md` говорит:
   фаза — чистка кодовой базы, источник истины — один ноутбук, API, UI и
   Docker не развивать. `PROJECT.md` называет целью «минимальный рабочий
   сценарий», что давно неправда. Новичок не может понять, чему верить.

Что при этом хорошо и что план сохраняет: маршрут по уровням понимания как
идея, диаграммы разных масштабов в `architecture.md`, словарь `Notations.md`,
игрушечные сценарии `scenarios.md`, перепроверяемые тестом
`test_docs_scenarios.py`, и разделы «Why It Is Built This Way».

## Принципы целевого состояния

- Проза несёт только то, чего нет в коде: зачем, инварианты, карту целого.
  Что делает конкретная функция — докстринг этой функции, не документ.
- Маршрут идёт от конкретного к общему: один велосипед → один период →
  журнал потоков → архитектура → модули.
- Справочник — не учебник. `Notations.md` открывают по мере надобности,
  а не читают перед кодом. Для старта достаточно пяти понятий.
- Первый запуск не требует внешних данных.
- Новый документ появляется, когда один и тот же вопрос возник дважды.
  Если нельзя назвать вопрос, на который документ отвечает, — документ
  не нужен.

## Целевая структура docs/

```text
README.md                  # корневой: что это, установка, запуск — уже есть
docs/
  README.md                # вход: четыре двери — запустить / понять / изменить / найти контракт
  first_run.md             # первый запуск на синтетическом сценарии, без данных
  concepts.md              # пять понятий с одним примером каждое
  explanation/             # сжатые документы: карта кода + идея + диаграмма + почему так
  how-to/                  # рецепты задач, по одной странице
  reference/               # Notations.md (ссылка), api.md, команды — для поиска, не для чтения
  decisions/               # короткие записи о решениях, которые нельзя вывести из кода
  plans/                   # действующие планы (этот файл)
```

`docs/method/` остаётся личным материалом автора и из маршрута новичка
убирается. `docs/archive/` из репозитория удаляется — историю хранит git.

## Этапы

Порядок обязателен: сначала согласование и вход, сжатие больших документов —
последним. Сжимать текст, на который ещё указывает маршрут, — двойная работа.

### Этап 0. Согласовать источники истины

Что сделать:

- Привести `AGENTS.md` в соответствие с `CLAUDE.md`: одна и та же фаза, два
  канонических запуска (реплей истории и прогон на прогнозе, Notations.md
  §11), одинаковые команды. Проще всего сделать `AGENTS.md` копией или
  ссылкой на `CLAUDE.md`.
- `PROJECT.md` либо удалить, либо оставить только раздел «Principles»
  и перенести его в `CLAUDE.md`.

Критерий готовности: в корне нет двух файлов с разными ответами на вопросы
«какая сейчас фаза» и «что является каноническим сценарием».

### Этап 1. Первый запуск без данных

Что сделать:

- Написать `docs/first_run.md`: читатель запускает синтетический сценарий
  из готовых построителей `tests/scenarios.py` (начать с `single_trip`,
  затем `overflow`) и смотрит на результат — строки журнала потоков и
  изменение инвентаря. Один код-блок на запуск, одна таблица с ожидаемым
  журналом, две-три фразы, что в ней читать.
- В том же документе — короткий раздел «запуск на реальных данных»: откуда
  берутся CSV, сколько весят, команда загрузки. Это отделяет «попробовать
  за минуту» от «развернуть по-настоящему».

Критерий готовности: человек с чистым клоном репозитория и установленным
окружением получает первый журнал потоков быстрее чем за десять минут, не
скачивая данные.

### Этап 2. Перестроить вход

Что сделать:

- Переписать `docs/README.md` как выбор из четырёх дверей: «запустить»
  (→ first_run.md), «понять» (→ concepts.md, затем сценарии 1–3 из
  scenarios.md, затем architecture.md), «изменить» (→ how-to/), «найти
  точный контракт» (→ Notations.md и reference/). Методику пяти уровней
  оставить ссылкой для интересующихся, не преамбулой.
- Написать `docs/concepts.md`: пять понятий, каждое — два-три предложения
  и один маленький пример. Понятия: период, спрос, инвентарь станции,
  журнал потоков, артефакт запуска. Каждое понятие ссылается на свой
  раздел `Notations.md` за точным контрактом.

Критерий готовности: путь новичка до первой осмысленной строки журнала —
три коротких документа (README → first_run → concepts), ни один не длиннее
150 строк.

### Этап 3. Рецепты задач

Что сделать: завести `docs/how-to/` и написать первые рецепты, по одной
странице каждый. Стартовый список:

- изменить спрос сценария (масштаб, свой файл);
- запустить прогон на прогнозе;
- добавить таблицу в артефакт запуска;
- добавить фазу в симулятор;
- разобраться с нарушением инварианта I1–I5.

Формат рецепта: задача в одну фразу, шаги с реальными командами и файлами,
ожидаемый результат. Рецепт пишется тогда, когда задача реально возникла, —
список выше не обязателен к немедленному заполнению целиком.

Критерий готовности: есть каталог `docs/how-to/` минимум с двумя рецептами,
и вход «изменить» в `docs/README.md` ведёт на него.

### Этап 4. Сжать explanation-документы

Что сделать, для каждого файла `docs/explanation/*.md`:

- Оставить четыре части: карта кода (таблица файлов — она уже есть и
  хороша), главная идея в несколько абзацев, одна диаграмма, раздел
  «почему так» с отвергнутыми альтернативами.
- Пошаговый пересказ функций удалить. То, что из пересказа жалко терять,
  перенести в докстринг соответствующего модуля или функции — там текст
  лежит рядом с кодом и виден при чтении.
- Разделы «Why It Is Built This Way» вынести короткими записями в
  `docs/decisions/` (одна запись — одно решение: журнал как источник истины,
  зачем нужен sizing run, почему прогноз заменяет только таблицу спроса)
  либо оставить на месте — решить по ходу, но не дублировать.

Ориентир объёма: 100–150 строк на документ вместо 300–750. `scenarios.md`
не сжимать: его таблицы проверяются тестами и являются учебным материалом.

Критерий готовности: суммарный объём `docs/explanation/` сократился хотя бы
вдвое, и ни один документ не описывает тело функции, у которой есть докстринг.

### Этап 5. Уборка

Что сделать:

- Удалить `docs/archive/` (17 файлов; история остаётся в git).
- Просмотреть `docs/reports/` и `docs/plans/`: выполненные планы и старые
  отчёты удалить, действующие оставить.
- Русские дубликаты держать только для файлов, которые автор реально
  перечитывает. `ml_ru.md` удалить, если он не из их числа.

Критерий готовности: в `docs/` нет файлов, на которые не ведёт ни одна
ссылка из `docs/README.md`, кроме reference-материалов.

## Чего не делать

- Не начинать со сжатия больших документов: пока маршрут не перестроен,
  непонятно, какой текст вообще останется нужным.
- Не писать новые обзорные документы «про всё»: добавлять только страницы,
  отвечающие на конкретный вопрос.
- Не переводить документы на русский по умолчанию: канонический язык
  документов — английский, русская копия — только по явной просьбе.
  Этот план — исключение по просьбе автора.

## Критерий готовности всего плана

- Первый запуск: с чистого клона до первого журнала потоков — меньше десяти
  минут, без скачивания данных.
- Объём: живая документация (без reference) читается за один вечер.
- Непротиворечивость: `CLAUDE.md`, `AGENTS.md` и корневой `README.md` дают
  один и тот же ответ про фазу и канонический сценарий.
- Практический тест: когда у автора возникает вопрос о системе, он сам
  открывает документацию — и находит ответ либо в ней, либо по её ссылке
  в код.
