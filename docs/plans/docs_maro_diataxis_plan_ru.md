Рабочий план автора, по-русски (как и предыдущий план документации —
исключение из правила «документы на английском»). План самодостаточен:
его можно выполнять из нового чата, не читая прошлых обсуждений.

Предшественник — `docs/plans/docs_rework_plan_ru.md` — выполнен: вход с
четырьмя дверями есть, `first_run.md` и `concepts.md` написаны, `how-to/`
заведён, explanation-документы сжаты до 100–190 строк. Этот план надстраивает
следующий уровень: навигация как у MARO (https://maro.readthedocs.io),
типы содержимого — по Diátaxis (https://diataxis.fr), плюс новое
позиционирование проекта как фреймворка для потоковых графов.

## Идея объединения

MARO и Diátaxis отвечают на разные вопросы и не конфликтуют.

- MARO даёт имена разделов навигации — «из чего состоит продукт»:
  Installation, Quick Start, Key Components, Scenarios.
- Diátaxis даёт правило содержимого — «какого типа текст внутри страницы»:
  tutorial (учебный маршрут по шагам), how-to (рецепт задачи),
  reference (точный контракт для поиска), explanation (устройство и «почему»).

Объединение: снаружи разделы называются как у MARO, внутри каждая страница —
ровно один тип Diátaxis. Типы не смешиваются на одной странице: в
объяснении нет пошаговых инструкций, в рецепте нет теории.

Соответствие разделов и типов:

| Раздел (имя как у MARO) | Тип по Diátaxis | Что это у нас |
|---|---|---|
| Getting Started (Installation + Quick Start) | tutorial | установка, первый запуск без данных, запуск UI |
| Key Components | explanation | нынешние `explanation/*.md` |
| Scenarios | explanation со ссылками на код и ноутбуки | новая длинная страница про Citi Bike |
| How-to | how-to | нынешний `docs/how-to/` (у MARO такого раздела нет — сохранить) |
| Reference | reference | `Notations.md`, контракт API, таблица команд |

Правило против дублирования между Key Components и Scenarios (как у MARO):
страницы компонентов описывают механизм один раз (что такое фаза, журнал
потоков, загрузчики); страница сценария описывает конкретный кейс от начала
до конца (какие CSV, какие конфиги, какие запуски, какие результаты) и на
механизм только ссылается. Доменные слова («станция», «велосипед») на
страницах компонентов допустимы как примеры — код доменный, притворяться
абстрактным не нужно. Запрещено другое: описывать один механизм в двух местах.

## Правила содержимого (действуют на каждом этапе)

- Простой английский, короткие предложения, без образных слов. Имена из кода
  (`step_id`, `finalize_flows`, `facility_id`) не переводить и не
  перефразировать. Словарь — `Notations.md`: одно понятие, одно слово.
- Факт-чек перед правкой: каждое поведенческое заявление («строит»,
  «записывает», «читает», «сохраняет») проверить по строке кода, которая его
  доказывает. Порядок выполнения проверять по реальному раннеру, конструктору
  или списку фаз. Что нельзя быстро проверить — смягчить или убрать.
- Одна страница — один тип Diátaxis. Учебные страницы: повелительное
  наклонение, ожидаемый вывод после каждого шага, ноль теории. Объяснения:
  ни одной пошаговой инструкции, вместо неё ссылка на tutorial или how-to.
- Не обещать инфраструктуру, которой нет. Docker compose есть — писать можно.
  Кластеров на Azure нет — раздел не заводить даже как «coming soon».
- Разделы «Why It Is Built This Way» в перевезённых документах сохранить.
