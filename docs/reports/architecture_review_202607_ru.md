# Обзор архитектуры: где одно знание живёт в нескольких местах

Дата обзора: 2026-07-11. Статус: только предложения — код не менялся.

Этот документ перечисляет десять мест, где кодовая база заставляет держать
одно и то же знание в нескольких файлах, и предлагает, как собрать каждое
знание в одном месте. Каждый пункт проверен по коду: фрагменты ниже — настоящие,
с файлом и номером строки. Пункты отсортированы по частоте трения: первые
задевают почти каждую правку в своём слое, последние — дешёвые чистки.

## Словарь документа

Пять слов, которыми описаны все пункты. Они взяты из внутреннего скилла
архитектурного обзора и используются в одном и том же смысле во всём документе.

- Интерфейс модуля — всё, что нужно знать, чтобы правильно пользоваться
  модулем. Не только сигнатура функции: ещё порядок вызовов, договорённости
  о колонках, невидимые правила вида «сначала вызови настройку».
- Глубокий модуль — за маленьким интерфейсом спрятано много работы. Пример
  из проекта: `round_forecast_demand` — одна функция, а за ней всё правило
  округления дробного прогноза до целых велосипедов.
- Мелкий модуль — противоположность: чтобы вызвать модуль, нужно знать почти
  столько же, сколько написано у него внутри. Крайний случай — проходной
  модуль: он только передаёт вызов дальше.
- Шов — место, где живёт интерфейс. В этом месте реализацию можно заменить
  (диск на HTTP, одну модель на другую), не редактируя вызывающих. Пример:
  переключатель `API_URL` — страницы читают таблицы, не зная, диск это или
  сервер.
- Локальность — правило записано в одном месте и меняется в одном месте.
  Противоположность: правило скопировано в три файла, и копии совпадают,
  только пока никто не забыл поправить все три.

И один приём — тест удаления. Чтобы понять, полезен ли модуль, мысленно
удаляем его. Если сложность исчезла — модуль ничего не прятал. Если та же
логика всплывает у всех вызывающих — модуль работал, его стоит углублять,
а не удалять.

## 1. Инвентарь для решений внутри фазы

Как устроено сейчас. У состояния симулятора один путь записи: фаза строит
события и отдаёт их `apply_step_events`, и только там инвентарь двигается по
правилу «+1 за докование, −1 за отправление»:

```python
# gbp/consumers/simulator/state.py:240
deltas = inventory_deltas_from_events(flows)
inventory = (
    self.state_inventory_df
    if deltas.empty
    else adjust_inventory(self.state_inventory_df, deltas)
)
```

Но фаза принимает решения по ходу работы. Куда отправить велосипед,
отскочивший от полной станции, зависит от того, сколько доков только что
заняли плановые докования этой же фазы. Записать их в состояние фаза ещё не
может — запись одна, в конце. Поэтому она считает себе локальную копию
инвентаря:

```python
# gbp/consumers/simulator/phases.py:154
after_docked = adjust_inventory(
    state.state_inventory_df, inventory_deltas_from_events(arrivals_docked)
)
```

Внутри механики редиректа — ещё одна копия, обновляемая каждый раунд:

```python
# gbp/consumers/simulator/mechanics.py:243
running = adjust_inventory(running, dock_deltas(docked_now, "realized_target_id"))
```

Третья такая копия живёт в `ApplyRebalancingPhase`
(`gbp/consumers/simulator/rebalancing.py:734-805`): она проводится через три
раунда фазы.

Чем это мешает. Правило «как события двигают инвентарь» применяется в
настоящем пути записи и ещё примерно в пяти местах решений. Все копии обязаны
давать тот же результат, что настоящая запись, но это нигде не гарантировано —
расхождение ловит только инвариант I3, и только в конце рана. Каждая новая
фаза с решениями посередине начнёт с ещё одной ручной копии.

Что предлагается. Углубить интерфейс состояния: дать фазе операцию, которая
применяет уже готовую часть событий и возвращает инвентарь, каким его должно
видеть следующее решение. Тогда фаза не считает инвентарь сама — она всегда
получает его из одних рук.

Что это даст. Правило «+1/−1» останется записанным в одном месте. Инвариант
I3 перестанет быть единственной защитой от расхождения. Тесты фаз перестанут
проверять бухгалтерию, которую фаза больше не ведёт.

## 2. Порядок шагов (`step_id`): нумерация размазана по пяти файлам

Как устроено сейчас. `step_id` — сквозной номер шага инвентаря
(Notations.md §0.1). Он появляется двумя путями. Симулятор выдаёт номер
счётчиком в момент записи (`SimulationState.open_step`). Исторический
загрузчик фаз не имеет, поэтому `finalize_flows` выводит номер из тройки
`(period_id, phase_rank, phase_round)`. Обе ветки живут в одной функции:

```python
# gbp/model/flows.py:702
stamped = "step_id" in flows.columns and not flows["step_id"].isna().all()
if stamped:
    # Trust the stamped number; order by it, then by the trip ids within a step.
    ...
# Derive: number the distinct (period_id, phase_rank, phase_round) tuples.
```

Чтобы проследить путь одного номера, нужно пройти пять мест: фаза объявляет
свой `phase_rank` (`phases.py`, `rebalancing.py`); механика редиректа нумерует
раунды `phase_round` (`mechanics.py:236`); состояние открывает шаг и штампует
номер (`state.py:236-238`); `finalize_flows` сортирует или перевыводит
(`flows.py:655-739`); движок отдельно проверяет, что список фаз отсортирован
по рангу (`engine.py:59-63`).

Чем это мешает. У номера два определения — «выданный счётчиком» и
«выведенный из тройки», — и для исторических событий они обязаны давать один
и тот же порядок. Это совпадение охраняет единственный тест
(`tests/test_scenarios.py:181-204`). Автор новой фазы должен выучить все пять
мест, хотя от него требуется одно: писать события через `apply_step_events`.

Что предлагается. Собрать выдачу и штамповку номера у одного владельца —
состояние уже почти владелец через `open_step`. Ветку «вывести номер из
тройки» оставить только историческому загрузчику, которому она законно нужна,
и держать её рядом с ним, а не в общем пути всех событий.

Что это даст. На вопрос «откуда у события `step_id`» будет один ответ для
каждого пути. Правило для автора фазы сожмётся до одной строки.

## 3. Симулятор зависит от всего загрузчика, а читает около 11 полей

Как устроено сейчас. Каждая фаза, движок, валидатор и сайзинг типизированы
классом загрузчика `ResolvedModelData` — у него больше 25 атрибутов
(`gbp/loaders/dataloader_graph.py:778-918`). Реально симулятор читает около
11 из них. Точный список виден в тестовой подделке, которая собирает вход
симулятора вручную:

```python
# tests/scenarios.py:101
resolved = types.SimpleNamespace()
resolved.periods_df = periods
resolved.facilities_geo_df = geo
resolved.facilities_df = pd.DataFrame(...)
resolved.commodities_categories_df = pd.DataFrame(...)
resolved.facilities_capacities_df = pd.DataFrame(...)
resolved.initial_inventory_df = pd.DataFrame(...)
resolved.historical_flows_df = hist
resolved.historical_demand_df = J.flows_to_departures(hist)
resolved.historical_od_matrix_df = J.flows_to_od_matrix(hist)
resolved.trip_speed_km_per_period = 15.0
resolved.routes = Routes(...)
```

Это и есть настоящий интерфейс симулятора — но он нигде не назван. Тесты
поддерживают его руками, и два тестовых хелпера (`build_resolved` и
`with_rebalancing_data`) уже перечисляют разные наборы полей.

Чем это мешает. Симулятор знает про загрузчик, хотя ему нужны только входные
таблицы одного сценария. Узнать, что именно нужно фазам, можно только чтением
их кода или тестовой подделки. Добавление поля в загрузчик выглядит как
изменение интерфейса симулятора, хотя им не является.

Что предлагается. Назвать контракт: тип «входные таблицы одного сценария»
с теми полями, которые симулятор действительно читает. `ResolvedModelData`
остаётся продуктом загрузчика и становится одним из поставщиков этого
контракта. Тестовая подделка становится вторым поставщиком — уже законным,
а не самодельным.

Что это даст. Симулятор перестаёт зависеть от загрузчика. Список «что нужно
фазам» существует в одном месте и проверяется типом, а не дисциплиной.
Страница `docs/explanation/architecture.md` уже описывает этот узкий поднабор
словами — он станет кодом.

## 4. Операция «спрогнозировать месяц» собирается вручную в четырёх файлах

Как устроено сейчас. Всюду, где слой прогнозирования превращает имя месяца
в предсказание, повторяется один рецепт: границы месяца → часовая сетка
периодов → история до месяца → `forecast_input` → предсказание → округление.
Ключевая строка рецепта скопирована трижды:

```python
# gbp/ml/backtest.py:144, gbp/ml/monitoring.py:190, gbp/ml/training.py:188
horizon = get_forecast_periods_df(
    start, int((end - start) / DEFAULT_PERIOD_LEN), DEFAULT_PERIOD_LEN
)
```

А функция чтения фактических счётчиков месяца существует в двух файлах
дословно, и ни один не импортирует другой:

```python
# gbp/ml/backtest.py:153 и gbp/ml/monitoring.py:161 — одна и та же функция
def load_actual_month(month, root=None):
    path = partition_path(month, root)
    if not path.exists():
        raise FileNotFoundError(...)
    return pd.read_parquet(
        path, columns=["period_id", "facility_id", "commodity_category", "quantity"]
    )
```

Построители прогноза в `forecast.py:378-546` собирают тот же рецепт третьим
способом — через `month_bounds` и свои переменные.

Чем это мешает. Копии совпадают, пока никто не забыл поправить все.
Изменение рецепта — например, переход на другую длину периода — это правка
в четырёх местах, и пропущенное место не упадёт, а начнёт тихо считать
по-старому.

Что предлагается. Один модуль «прогноз месяца»: по имени месяца — сетка
горизонта, по модели и горизонту — предсказание. Его зовут построитель
прогноза, бэктест и мониторинг. Чтение фактических счётчиков — одна функция
рядом с `partition_path` в `training.py`.

Что это даст. Рецепт станет одним местом с одним тестом. Сегодняшние три
копии проверяются только тем, что пока никто не менял одну без других.

## 5. Интерфейс семейства моделей обходят в трёх местах

Как устроено сейчас. Все четыре семейства моделей живут за одним интерфейсом
`DemandModel` (`fit` / `predict`), и правило проекта — конструировать их
только через фабрику `create_model`. На предсказании интерфейс честный: ни
один вызывающий не различает семейства. Но есть три обхода.

Первый: мониторинг строит наивный прогноз, минуя фабрику, — импортирует
конкретный класс:

```python
# gbp/ml/monitoring.py:193
fractional = SeasonalNaiveModel().predict(forecast_input(history, horizon))
```

Второй: сама фабрика неоднородна. Параметры `train_months` и `raw` нужны
только семейству `graphsage` (по ним фабрика строит рёбра графа из сырых
поездок — `gbp/ml/models/__init__.py:59-69`), но передают их все четыре
вызывающих, включая тех, кто создаёт `seasonal_naive`.

Третий: идея «сезонный наивный — мерило качества» реализована дважды разной
математикой. Бэктест считает отношение ошибок (`mae_over_naive`,
`backtest.py:165-180`), мониторинг — скользящее среднее против порога
(`degraded`, `monitoring.py:278-311`), и каждый строит наивный прогноз
по-своему.

Чем это мешает. Правило «семейства конструируются только через фабрику»
нарушает собственный код платформы. Смысл «модель хуже наивной» может
разойтись между бэктестом и мониторингом незаметно — общего наивного прогноза
у них нет.

Что предлагается. Построение графовых рёбер убрать внутрь `fit` семейства
`graphsage` — обучающая таблица у него уже есть, и фабрика станет однородной:
имя семейства и ничего лишнего. Наивный прогноз месяца — одна функция через
фабрику, которую читают и бэктест, и мониторинг.

Что это даст. У шва семейств не останется особых случаев со стороны
вызывающих. Мерило «против наивного» будет опираться на один и тот же
прогноз в обоих местах.

## 6. Глобальное состояние MLflow и скрытый контракт бэктеста с пайплайном

Как устроено сейчас. `configure_mlflow` настраивает MLflow на весь процесс:

```python
# gbp/ml/registry.py:55
mlflow.set_tracking_uri(f"sqlite:///{store / 'mlflow.db'}")
```

Правило «сначала вызови настройку» не видно ни в одной сигнатуре, поэтому
каждая функция реестра вызывает её на входе на всякий случай — всего
одиннадцать защитных вызовов в `registry.py`, `backtest.py` и `pipeline.py`.

Вторая половина проблемы: пайплайн достаёт результат бэктеста обратно из
MLflow и для этого знает его внутреннюю раскладку — имя рана `comparison`
(`pipeline.py:316`), имя файла `comparison.csv` (`pipeline.py:326`), префикс
`params.` у колонок (`pipeline.py:331-333`) и ключ `data_version`
(`pipeline.py:514`). Четыре строковые константы, продублированные между двумя
файлами без общего типа: поменяешь одну сторону — вторая молча перестанет
находить результаты.

Что предлагается. Хранилище MLflow сделать объектом, который создаётся один
раз и передаётся дальше, — тогда правило порядка несёт само значение, а не
дисциплина вызывающих. Для сравнения моделей завести пару «записать
сравнение / прочитать последнее сравнение» внутри бэктеста, чтобы пайплайн
не знал ни имён ранов, ни имён файлов.

Что это даст. Одиннадцать защитных вызовов исчезнут. Раскладка MLflow будет
знанием одного модуля. Тесты шага promote перестанут собирать состояние
MLflow руками.

## 7. Переключатель «диск или API» проверяется в пяти местах, а страница запуска идёт мимо

Как устроено сейчас. Комментарий в `ui_shared.py:64` называет модуль
единственной дверью к сохранённому рану: страница просит таблицу, а выбор
бэкенда (локальные файлы или HTTP при заданном `API_URL`) спрятан внутри.
Для чтения это почти правда, но сам выбор повторяется пять раз:
`list_runs` (`ui_shared.py:71`), `_table_cached` (`:79`), `table_cache_key`
(`:97`), `_meta_cached` (`:142`) и `load_meta` (`:149`) — причём `load_meta`
проверяет `api_client.api_url()` дважды за один вызов.

А записывающая половина — запуск и опрос рана — вообще идёт мимо этой двери:

```python
# app/views/run_scenario.py:62
answer = api_client.start_run(request)
```

Страница запуска импортирует `api_client` напрямую и сама ветвится на
`api_url` (`run_scenario.py:12, 62, 68, 82`).

Чем это мешает. Читатель, выучивший «переключатель живёт в `ui_shared`»,
ошибается ровно для той страницы, которая пишет. Пять точек ветвления — пять
мест, где поведение двух бэкендов может разойтись. Страница запуска из-за
переплетения с `api_client` не входит в смоук-тест страниц (список `PAGES`
в `tests/test_app_artifacts.py:269-278`).

Что предлагается. Одно место, где выбирается бэкенд, и через него — и чтение
таблиц, и запуск с опросом рана. Страницы не импортируют `api_client`.

Что это даст. Проверка «мы на API или на диске» будет одной. Страницу
запуска можно будет включить в смоук-тест.

## 8. Сохранение результата рана скопировано дважды, а evaluate.py восстанавливает выброшенные значения

Как устроено сейчас. Цепочка «собрать таблицы → собрать meta → сохранить»
повторена почти дословно в двух файлах: `app/runner.py:207-238` и
`app/evaluate.py:206-230`. Оба вручную снимают одни и те же восемь аргументов
с результата рана и данных сценария:

```python
# app/runner.py:207 и app/evaluate.py:206 — одинаковый блок
tables = artifacts.build_run_tables(
    result.simulated_flows_df,
    initial_inventory=result.initial_inventory_df,
    facilities=data.facilities_df,
    facilities_geo=data.facilities_geo_df,
    facilities_capacities=result.facilities_capacities_df,
    rates=data.commodities_categories_rates_df,
    period_len=data.period_len,
    routes=data.routes,
)
```

— и ещё около десяти аргументов в `build_meta`. Третья копия той же цепочки
живёт в тестовой подделке (`tests/test_app_api.py:58`).

Дальше `evaluate.py` восстанавливает размерное состояние рана из внутренностей
таблиц — значения, которые у сборщика были в руках и не были сохранены:

```python
# app/evaluate.py:259
"initial_inventory_bikes": int(panel.loc[panel["period_id"] == 0, "quantity_sop"].sum()),
"station_capacity_docks": int(stations["capacity"].fillna(0).sum()),
```

Чем это мешает. Любое изменение контракта `build_meta` — правка в трёх
местах. А восстановление размерного состояния из panel нарушает правило
проекта «читатель не вычисляет то, что сборщик может предвычислить»: чтобы
прочитать эти две цифры, `evaluate.py` должен знать, какая колонка panel и
какая категория facilities означают «размерное состояние».

Что предлагается. `artifacts.py` получает одну операцию «сохранить результат
сценария как run artifact» — она сама снимает нужные поля с результата и
данных. Стартовый инвентарь и ёмкость станций предвычисляются в `meta.json`
при сборке.

Что это даст. Контракт сборки меняется в одном месте. `evaluate.py`
возвращается в роль чистого читателя.

## 9. Страницы заново знают раскладку таблиц, подписи и пути

Как устроено сейчас, три примера. Станционная карта строит сравнение двух
ранов вручную — переименовывает каждую колонку panel в пару с суффиксом `_b`
и вычитает:

```python
# app/views/station_map.py:52
slice_b = slice_b.rename(columns={name: f"{name}_b" for name in PANEL_VALUES})
data = data.merge(slice_b, on="facility_id", how="left")
...
data["value"] = data[f"{metric}_b"] - data[metric]
```

Страница объекта держит строковый кортеж «эти колонки — инвентарь, не поток»
(`app/views/facility_detail.py:72`: `("quantity_sop", "quantity_eop")`), хотя
описание метрик уже централизовано в таблице `METRICS`. Подпись метрики
вида `"Redirected (redirected)"` в одном месте собирается, а в другом
разбирается обратно строковой операцией `label.split(" (")`
(`app/ui_shared.py:294`). Путь `run_dir/<имя таблицы>.parquet` построен
заново в `app/api.py:208` и `app/ui_shared.py:86`, а `run_scenario.py:191`
показывает пользователю строку `f"data/runs/{run_name}"`, которая разойдётся
с настоящим путём, если задан `DATA_DIR`.

Чем это мешает. Знание «какие колонки у panel и arcs и что они значат»
расползается из `artifacts.py` по страницам. Добавление метрики или
переименование колонки задевает страницы, которые по правилу проекта должны
только рисовать готовое.

Что предлагается. Сравнение двух панелей (A, B, разность) — общая функция
рядом с `panel_slice`. Признак «инвентарная колонка» — поле описания метрики
в `METRICS`, а не кортеж в странице. Пути к файлам артефакта отдаёт
`artifacts.py`, и все берут их оттуда.

Что это даст. Правило «страница не называет parquet-файл и не знает колонок»
станет правдой, а `METRICS` останется единственным описанием метрики.

## 10. Мелкие правила без хозяина (симулятор)

Пять независимых чисток. Каждая маленькая, но каждая — правило, которое
сейчас совпадает между файлами только по договорённости.

Масштабирование спроса. Выражение повторено трижды дословно:

```python
# phases.py:221, validation.py:79, rebalancing.py:221
(quantity * demand_scale_factor).round().astype("Int64")
```

Валидатор обязан округлять так же, как фаза, иначе инвариант I1 сработает
ложно, — это записано только в докстринге (`validation.py:53-56`). Нужен один
помощник «масштабированный спрос периода», который читают все трое.

Общие доки. Правило «доки общие между типами велосипедов, поэтому занятость
станции — сумма по всем типам» выведено заново в четырёх местах:
`mechanics.py:50` (`free_docks`), `flows.py:1404` (объяснитель редиректа),
`rebalancing.py:265` (обрезка развозов), `dataloader_graph.py:719` (расчёт
ёмкостей). Нужен один помощник занятости, который зовут все четверо.

`dock_deltas`. Функция `state.py:44-59` — вторая запись докующей половины
правила «+1/−1» с единственным вызывающим (`mechanics.py:243`). Свести к
одному владельцу правила дельт.

Мёртвые свойства состояния. Пять свойств `state_departures_df`,
`state_arrivals_df`, `state_demand_df`, `state_supply_df`,
`state_od_matrix_df` (`state.py:138-167`) не имеют ни одного вызывающего в
`gbp/`, `app/` и `tests/` (проверено поиском), а `state_demand_df` и
`state_departures_df` совпадают дословно. Удалить.

Место математики сайзинга. Функции `get_replay_initial_inventory_df`,
`get_replay_capacities_df`, `get_saturated_inventory_df`
(`dataloader_graph.py:632-772`) читают журнал sizing run и служат только
сайзингу, но живут в загрузчике — из-за этого `sizing.py` импортирует их
«вверх» из загрузчика. Перенести их к `size_state_for_demand`.

## Здоровые глубокие модули — не трогать

Для равновесия: обзор отдельно отметил модули, где знание уже собрано в одном
месте. Их предложения выше не задевают.

- Журнал `gbp/model/flows.py`: событийная схема и все read-model'и за одним

  вход прогноза берут колонки отсюда, проверка «фичи не заглядывают в будущее»
  стоит в одной точке.
- `round_forecast_demand` (`gbp/ml/forecast.py`): правило округления прогноза
  решено один раз.
- Ядро `app/artifacts.py`: `METRICS`, `RunMeta`, схемы таблиц — одно описание
  каждой метрики и каждого файла артефакта.
- `app/api_client.py`: модуль мелкий, но тест удаления говорит «оставить» —
  без него знание про HTTP и декодирование ответов расползётся по `ui_shared`.
