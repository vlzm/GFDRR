# План развёртывания в интернете (Azure, до 10 пользователей)

Цель: текущее рабочее ядро (симулятор `gbp/` и Streamlit-приложение `app/`)
должно стать сайтом в интернете, которым пользуются до 10 человек.
Нагрузка маленькая, поэтому план сознательно выбирает простые управляемые
сервисы Azure и избегает тяжёлых инструментов (Kubernetes, Celery) там,
где хватает простых.

План разбит на этапы. Каждый этап заканчивается критерием готовности —
проверкой, что этап действительно завершён. Этапы идут в том порядке,
в котором их стоит делать: каждый следующий опирается на предыдущий.

---

## Что есть сейчас (точка старта)

- Код: пакет `gbp/` (симулятор) и `app/` (веб-интерфейс на Streamlit
  плюс запуск из терминала через `app/runner.py`).
- Данные лежат файлами на диске:
  - `data/raw/` — исходные CSV с поездками, ~3 ГБ;
  - `data/osrm/` — дорожный граф для сервера маршрутов, ~1 ГБ;
  - `data/runs/` — сохранённые результаты запусков (артефакты), ~33 МБ.
- OSRM — отдельный сервер, который считает расстояния по дорожной сети.
  Он уже запускается в Docker (`scripts/osrm/serve.sh`), приложение ходит
  к нему по адресу `http://127.0.0.1:5000`.
- Базы данных нет. Входа по паролю нет. Всё запускается вручную на одной машине.

Это нормальная точка старта: код уже разделён на «ядро», «интерфейс» и
«данные», поэтому упаковка в контейнеры будет простой.

---

## Целевая архитектура

Словарь для схемы ниже:

- Контейнер — упакованное приложение вместе со всеми его зависимостями,
  которое одинаково запускается на любой машине.
- Azure Container Apps — сервис Azure, который запускает контейнеры и сам
  следит за ними: перезапускает упавшие, выдаёт HTTPS-адрес, пишет логи.
  Не нужно администрировать виртуальную машину.
- Azure Files — сетевой диск в Azure. Его можно подключить к контейнеру
  как обычную папку, код при этом не меняется.

```
Пользователь (браузер)
        │  HTTPS + вход по Microsoft-аккаунту (Entra ID)
        ▼
Container App "app"  — Streamlit-интерфейс (внешний адрес)
        │  внутренняя сеть, наружу не виден
        ▼
Container App "osrm" — сервер маршрутов (только внутренний адрес)

Оба контейнера видят общий сетевой диск (Azure Files),
подключённый как папка /data:
    /data/raw   — исходные CSV
    /data/osrm  — дорожный граф
    /data/runs  — результаты запусков (пишет "app", читают все)
```

Почему именно Container Apps, а не альтернативы:

- Одна виртуальная машина с docker compose — дешевле и проще всего,
  но тогда обновления системы, HTTPS-сертификаты, перезапуски после сбоев
  и вход по паролю — твоя ручная работа. Для «максимально профессионально»
  это шаг назад.
- Kubernetes (AKS) — умеет всё то же, но требует отдельной экспертизы
  и стоит дороже. Для 10 пользователей это лишнее.
- Container Apps — середина: управляемый сервис, HTTPS и вход «из коробки»,
  при этом описывается в Terraform и выглядит в резюме и в жизни как
  взрослое решение.

## Этап 0. Подготовка кода к развёртыванию

Сейчас код рассчитан на запуск с одной машины: пути и адреса зашиты в
константы. Перед упаковкой в контейнеры их надо вынести в переменные
окружения — это значения, которые задаются снаружи при запуске, а не в коде.

Шаги:

1. Вынести в переменные окружения два значения:
   - `OSRM_URL` — сейчас зашит как `DEFAULT_OSRM_URL = "http://127.0.0.1:5000"`
     в `gbp/routing.py`. В контейнере адрес будет другим
     (`http://osrm:5000` локально, внутренний адрес в Azure).
   - `DATA_DIR` — корень папки данных. Сейчас пути собираются от корня
     репозитория (`_REPO_ROOT / "data" / ...` в `app/runner.py`).
     Чтение делать через `os.environ.get("OSRM_URL", DEFAULT_OSRM_URL)` —
     локальный запуск без переменных продолжит работать как раньше.
2. Зафиксировать зависимости. Сейчас в `pyproject.toml` указаны только
   нижние границы версий (`pandas>=2.0.0`). Для воспроизводимой сборки
   нужен файл со точными версиями: `uv lock`, файл `uv.lock` закоммитить.
3. Добавить `.dockerignore` (аналог `.gitignore` для сборки контейнера):
   исключить `data/`, `notebooks/`, `.venv/`, `__pycache__/`, `other_staff/`.
   Иначе 4 ГБ данных поедут внутрь образа.
4. Проверить, что приложение поднимается на чистой машине по инструкции
   из README: `uv pip install -e ".[ui]"` → `streamlit run app/main.py`.

Критерий готовности: приложение работает локально, при этом адрес OSRM
и путь к данным задаются переменными окружения, а не правкой кода.

Оценка: 0.5–1 день.

## Этап 1. Docker и docker compose

Docker-образ — это «слепок» приложения со всеми зависимостями.
docker compose — файл, который описывает несколько контейнеров и как они
соединены; одна команда `docker compose up` поднимает всё вместе.
Это и есть локальная копия будущей облачной архитектуры.

Шаги:

1. Написать `Dockerfile` для приложения. Основа:

   ```dockerfile
   FROM python:3.11-slim
   COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
   WORKDIR /srv
   COPY pyproject.toml uv.lock ./
   COPY gbp/ gbp/
   COPY app/ app/
   RUN uv pip install --system ".[ui]"
   EXPOSE 8501
   CMD ["streamlit", "run", "app/main.py", \
        "--server.port=8501", "--server.address=0.0.0.0"]
   ```

   Данные в образ не кладём: образ должен оставаться маленьким (~1–1.5 ГБ
   из-за ortools и pyarrow), а данные подключаются диском.

2. Написать `docker-compose.yml` с двумя сервисами:

   ```yaml
   services:
     app:
       build: .
       ports: ["8501:8501"]
       environment:
         OSRM_URL: http://osrm:5000
         DATA_DIR: /data
       volumes:
         - ./data:/data
       depends_on: [osrm]
     osrm:
       image: osrm/osrm-backend
       command: osrm-routed --algorithm mld --max-table-size 10000 /data/NewYork.osrm
       volumes:
         - ./data/osrm/bike:/data
   ```

   Сервер OSRM уже сейчас запускается через Docker в `scripts/osrm/serve.sh` —
   команду и параметры взять оттуда, чтобы поведение не разошлось.

3. Проверка честности: склонировать репозиторий в пустую папку
   (или на другую машину), положить `data/`, выполнить `docker compose up`.
   Всё должно работать без единого ручного шага сверх этого.

Критерий готовности: `docker compose up` на чистой машине поднимает
приложение и OSRM; сценарий запускается, артефакт появляется в `data/runs/`.

Оценка: 1–2 дня (включая знакомство с Docker).

## Этап 2. Данные: что где лежит

Главный принцип: не тащить базу данных туда, где её нет. Сейчас все данные —
файлы (CSV и parquet), и приложение читает их напрямую. Для 10 пользователей
это правильная схема, менять её не нужно. Нужно только выбрать, на чём эти
файлы лежат в облаке.

Раскладка:

| Данные | Объём | Где лежат в Azure | Почему |
|---|---|---|---|
| `data/raw/` (CSV поездок) | ~3 ГБ | Azure Files, папка `/data/raw` | читаются как обычные файлы, код не меняется |
| `data/osrm/` (дорожный граф) | ~1 ГБ | Azure Files, папка `/data/osrm` | OSRM требует файлы на диске |
| `data/runs/` (артефакты запусков) | ~33 МБ, растёт | Azure Files, папка `/data/runs` | пишутся приложением, должны переживать перезапуск контейнера |

Пояснения:

- Azure Files подключается к Container Apps как папка. Это самый дешёвый
  способ переехать в облако без изменения кода: приложение продолжает
  читать `/data/...` как локальный диск.
- Azure Blob Storage (хранилище «объектов», файлы доступны по URL, а не как
  папка) — стандартный выбор для больших данных, но потребовал бы менять
  код чтения. Отложить: имеет смысл, только если сырые данные вырастут
  в десятки гигабайт.
- Загрузка данных в облако — один раз, инструментом `azcopy`
  (консольная утилита Azure для копирования файлов):
  `azcopy copy ./data/* <адрес файлового хранилища> --recursive`.

Про PostgreSQL. Реляционная база на этом этапе не нужна: у приложения нет
ни пользовательских данных, ни одновременных записей, ни поиска по записям.
База станет нужна, когда появится хотя бы одно из:

- реестр запусков: кто, когда, с какими параметрами запускал сценарий,
  и в каком он статусе (эта информация не выводится из файлов надёжно);
- права доступа: какие запуски видит какой пользователь.

Когда это случится — взять Azure Database for PostgreSQL Flexible Server,
самый маленький размер (B1ms), одну таблицу `runs`
(`run_name`, `created_at`, `created_by`, `params_json`, `status`).
В `pyproject.toml` группа зависимостей `db` (sqlalchemy, alembic) уже есть.
Заводить базу заранее «на вырост» не надо: это +15$/мес и лишняя движущаяся
часть.

Критерий готовности: данные лежат в Azure Files, локальный compose умеет
работать и с локальной папкой, и (для проверки) со скачанной из облака копией.

Оценка: 0.5 дня.

## Этап 3. Ресурсы Azure и доступ пользователей

Список ресурсов, которые нужно создать (на этом этапе — руками через портал
или `az` CLI, чтобы понять каждый; на этапе 4 то же самое опишем кодом):

1. Resource Group — папка, в которой живут все ресурсы проекта.
   Например `rg-citibike-prod`.
2. Azure Container Registry (ACR) — хранилище docker-образов, откуда
   Container Apps их забирает. Тариф Basic.
3. Log Analytics Workspace — хранилище логов. Container Apps пишет туда
   вывод контейнеров автоматически.
4. Storage Account с файловым хранилищем (Azure Files) — диск `/data`
   из этапа 2.
5. Container Apps Environment — общая «площадка» для контейнеров:
   внутренняя сеть между ними и подключение дисков.
6. Container App `osrm` — образ `osrm/osrm-backend`, вход только
   внутренний (ingress internal), порт 5000, память 2 ГБ
   (дорожный граф Нью-Йорка держится в памяти).
7. Container App `app` — наш образ из ACR, вход внешний, порт 8501,
   минимум 1 копия (minReplicas = 1 — Streamlit держит открытое
   соединение с браузером, поэтому «спящий» режим с нулём копий не подходит),
   переменные `OSRM_URL` и `DATA_DIR`.

Вход пользователей. У Streamlit нет своей системы паролей. Правильное
решение для 10 человек — встроенная аутентификация Container Apps
(«Easy Auth»): Azure сам ставит перед приложением страницу входа через
Microsoft Entra ID (система учётных записей Microsoft; бывший Azure AD).
В коде не меняется ничего. Настройка: создать App Registration
(регистрацию приложения в Entra ID), включить authentication у Container App,
выдать доступ конкретным 10 учёткам. Люди без приглашения сайт не откроют.

Секреты (пароли, ключи). Сейчас секретов почти нет (ключ доступа к
файловому хранилищу, позже — пароль базы). Правило: секреты не лежат
в репозитории и не зашиты в образ. Хранить их в Azure Key Vault
(сервис-сейф для секретов) и передавать в Container Apps по ссылке.

Адрес сайта. Container Apps выдаёт адрес вида
`https://app.<случайное>.azurecontainerapps.io` с готовым HTTPS.
Для 10 человек этого достаточно; свой домен — по желанию, позже.

Про «Run scenario» надо понимать ограничение: кнопка Run в
`app/views/run_scenario.py` выполняет симуляцию прямо в веб-процессе.
Пока один пользователь запускает сценарий, приложение занято. Для старта
это приемлемо (10 человек, запуски редкие), но контейнеру `app` нужно
дать 4 ГБ памяти и 2 CPU. Как убрать это ограничение — этап 6.

Критерий готовности: приложение открывается по HTTPS-адресу из интернета,
пускает только приглашённых, сценарий запускается и артефакт сохраняется
в Azure Files (переживает перезапуск контейнера).

Оценка: 2–3 дня (больше всего времени уйдёт на Entra ID — это самая
запутанная часть Azure, закладывай время на чтение документации).

## Этап 4. Terraform

Terraform — инструмент, который описывает облачные ресурсы текстовыми
файлами. Вместо «накликал в портале и забыл как» получается код: его можно
читать, менять через pull request и накатить заново в новой подписке одной
командой. Terraform хранит состояние (state) — файл-опись того, что он уже
создал; для командной работы state держат не локально, а в облаке.

Шаги:

1. Bootstrap (единственное, что создаётся руками): Storage Account
   с контейнером `tfstate` под состояние Terraform.
2. Структура папки `infra/`:

   ```
   infra/
     providers.tf      # подключение провайдера azurerm, backend для state
     main.tf           # ресурсы: resource group, ACR, storage, environment,
                       # два container app, log analytics, key vault
     variables.tf      # входные параметры (имя окружения, размеры)
     outputs.tf        # что выдать наружу: адрес сайта, имя ACR
     envs/
       prod.tfvars     # значения параметров для prod
       dev.tfvars      # (по желанию) отдельное окружение для экспериментов
   ```

   Для одного проекта из ~10 ресурсов этого достаточно; на модули
   (переиспользуемые блоки Terraform) не разбивать — лишняя сложность.

3. Порядок освоения, чтобы не сломать работающее: сначала описать в
   Terraform копию окружения под другим именем (`rg-citibike-dev`),
   убедиться, что `terraform apply` собирает его с нуля до рабочего сайта,
   затем удалить ручное окружение из этапа 3 и создать prod уже Terraform-ом.
   Это проще и надёжнее, чем «импортировать» ручные ресурсы в state.
4. Проверка: `terraform destroy` + `terraform apply` в dev-окружении
   восстанавливает сайт без ручных шагов (кроме загрузки данных azcopy).

Критерий готовности: prod-окружение целиком описано в `infra/`,
`terraform plan` на чистом состоянии показывает «нет изменений».

Оценка: 2–3 дня.

## Этап 5. CI/CD (GitHub Actions)

CI (continuous integration) — на каждый pull request автоматически
запускаются проверки кода. CD (continuous delivery) — после слияния в main
новая версия автоматически собирается и выкатывается на сайт.
GitHub Actions — встроенный в GitHub исполнитель таких сценариев;
сценарии лежат в репозитории в `.github/workflows/`.

Два файла:

1. `ci.yml` — на каждый pull request:

   ```
   ruff check gbp/ tests/ app/
   ruff format --check gbp/ tests/ app/
   mypy gbp/
   pytest          (на небольшом тестовом наборе данных)
   docker build .  (проверка, что образ собирается)
   ```

2. `cd.yml` — на каждый push в main:

   ```
   docker build → тег = короткий хеш коммита (например app:8087fdf)
   push в ACR
   az containerapp update --image <acr>/app:8087fdf
   ```

   Тег хешом коммита, а не `latest`: всегда видно, какая версия кода
   работает на сайте, и можно откатиться на любой прошлый образ одной
   командой.

Доступ GitHub к Azure — через OIDC federated credentials: Azure доверяет
конкретному репозиторию GitHub без хранения пароля в секретах GitHub.
Это сегодняшний стандарт; ключи-пароли в секретах — устаревший способ.

Замечание про Terraform в CD: применять `terraform apply` автоматически
из CI на этом масштабе не нужно. Инфраструктура меняется редко — запускай
`terraform apply` руками с ноутбука, а CI пусть выкатывает только код.

Критерий готовности: слияние pull request в main без ручных действий
приводит к обновлению сайта через ~5–10 минут; в истории Actions видно,
какой коммит когда выехал.

Оценка: 1–2 дня.

## Этап 6. Фоновое выполнение сценариев (вместо Celery/Redis)

Проблема из этапа 3: симуляция выполняется внутри веб-процесса Streamlit.
Классическое решение — очередь задач: веб-приложение кладёт задачу в очередь
(Redis — быстрое хранилище, часто используемое как очередь), отдельный
процесс-работник (Celery — библиотека таких работников) её выполняет.

Для 10 пользователей есть решение проще и дешевле, без Redis и Celery:
Container Apps Jobs. Job — это контейнер, который запускается по требованию,
выполняет одну команду и умирает. У нас уже есть готовая команда — CLI-раннер:

```
python app/runner.py --run-name demand_x2 --demand-scale 2.0 --periods 50
```

Схема:

1. Описать в Terraform job `run-scenario` на том же образе, что и `app`,
   с тем же диском `/data`.
2. Кнопка Run в `app/views/run_scenario.py` вместо вызова симуляции
   в своём процессе запускает job с параметрами (через Azure SDK for Python)
   и сразу освобождает интерфейс.
3. Страница показывает статус: job работает / упал / готов; готовый запуск
   появляется в списке на главной странице как обычно, потому что артефакт
   лежит в `/data/runs/`.
4. Статус хранить просто: файл `status.json` рядом с артефактом запуска
   (`queued` → `running` → `done`/`failed`). Никакой базы для этого не надо.

Что это даёт по сравнению с Celery + Redis: тот же результат
(интерфейс не блокируется, запуски идут параллельно), но на две движущиеся
части меньше — нечему падать, нечего мониторить, не за что платить.
Celery станет оправдан, только если появятся сотни задач в день, приоритеты
и повторные попытки — на 10 пользователях этого не будет.

Этот этап делать после этапов 1–5, и только когда синхронный запуск
реально начнёт мешать (двое захотят запустить сценарий одновременно).

Критерий готовности: запуск сценария не блокирует интерфейс; упавший запуск
виден как failed с логом; два пользователя могут запустить сценарии
одновременно.

Оценка: 2–3 дня.

## Этап 7. Эксплуатация: логи, резервные копии, деньги

Минимальный набор, который делает сервис обслуживаемым:

1. Логи. Вывод контейнеров автоматически попадает в Log Analytics.
   Научиться двум вещам: смотреть живой лог
   (`az containerapp logs show -n app --follow`) и искать по истории
   в портале (Log Analytics, таблица `ContainerAppConsoleLogs_CL`).
   В коде уже используется structlog — этого достаточно, ничего не добавлять.
2. Оповещения. Два alert-правила в Azure Monitor: приложение перезапускается
   чаще N раз в час; сайт не отвечает на проверку живости
   (у Streamlit есть встроенный путь `/_stcore/health`).
   Оповещение — письмом, этого хватит.
3. Резервные копии. Код — в git. Данные: включить snapshots (снимки
   состояния) для Azure Files раз в сутки, хранить 14 дней. Этого достаточно:
   сырые данные восстановимы из первоисточника, артефакты пересчитываемы,
   snapshots защищают от «случайно удалил папку runs».
4. Деньги. Создать budget в Azure с оповещением на 50$ и 80$ в месяц.
   Ожидаемая стоимость окружения:

   | Ресурс | $/мес (примерно) |
   |---|---|
   | Container App `app` (1 копия, 2 CPU / 4 ГБ) | 15–35 |
   | Container App `osrm` (1 копия, 1 CPU / 2 ГБ) | 10–20 |
   | Azure Files (5 ГБ) + снимки | 1–3 |
   | Container Registry (Basic) | 5 |
   | Log Analytics | 3–5 |
   | Entra ID, HTTPS, Key Vault | ~0 |
   | Итого | ~35–70 |

   Главная ручка экономии: у OSRM поставить minReplicas = 0
   (контейнер засыпает, первый запрос после простоя ждёт ~1 минуту) —
   годится, потому что OSRM нужен только в момент построения графа.

5. Обновление данных. Процедура на будущее, когда появятся новые CSV
   или новая карта: локально `scripts/osrm/download.sh` + `build.sh`,
   затем `azcopy` в Azure Files, затем перезапуск `osrm`.
   Записать эту процедуру в README одним блоком команд.

Критерий готовности: письмо-оповещение приходит при падении сайта;
известна фактическая стоимость за первый месяц; процедура обновления
данных записана и один раз пройдена.

Оценка: 1 день.

## Сводный порядок работ

| # | Этап | Результат | Оценка |
|---|---|---|---|
| 0 | Подготовка кода | конфигурация через переменные окружения, uv.lock | 0.5–1 д |
| 1 | Docker + compose | `docker compose up` поднимает всё на чистой машине | 1–2 д |
| 2 | Данные | данные в Azure Files, решение по базе зафиксировано | 0.5 д |
| 3 | Azure вручную | сайт в интернете, вход только для приглашённых | 2–3 д |
| 4 | Terraform | всё окружение описано кодом, dev пересоздаётся с нуля | 2–3 д |
| 5 | CI/CD | merge в main сам выкатывает новую версию | 1–2 д |
| 6 | Фоновые запуски | Run не блокирует интерфейс (Container Apps Jobs) | 2–3 д |
| 7 | Эксплуатация | логи, оповещения, снимки данных, бюджет | 1 д |

Итого порядка 10–15 рабочих дней с учётом изучения незнакомых инструментов.
Этапы 0–3 дают работающий сайт; 4–5 делают его профессионально
поддерживаемым; 6–7 — удобным и надёжным. После этапа 3 сервисом уже
можно пользоваться.

Чего в плане сознательно нет (и не нужно на этом масштабе):
Kubernetes, Celery, Redis, собственный домен и балансировщик, кэш-слой,
несколько регионов, автоматический `terraform apply` из CI. Каждый из этих
пунктов добавляет постоянную сложность, а выгоду даёт только при нагрузке,
которой у сервиса на 10 человек не будет.
