# Архитектурный обзор: что стоит упростить

Дата: 2026-07-04. Ветка на момент проверки: `city_bike_mvp_accounting`.

Предыдущий обзор (`docs/architecture_review.md`, 2026-07-03) касался `gbp/`.
Все пункты из него уже были реализованы. Этот документ проверяет то, что не
попало в прошлый обзор или изменилось после него: слой `app/`, модуль
`gbp/routing.py`, а также новые расчёты стоимости, расстояния и времени по
часам.

Каждый вывод был сверён с кодом на момент обзора. В документе оставлены ссылки
на файлы и строки. Номера строк со временем могут измениться, но имена функций
и файлов должны остаться понятными.

## Термины

- **Модуль** — функция, класс или пакет, у которых есть входы, выходы и своя
  внутренняя логика.
- **Интерфейс** — всё, что нужно знать вызывающему коду: типы данных, порядок
  вызовов, правила, ошибки и настройки. Это не только сигнатура функции.
- **Глубокий модуль** — модуль, который делает много работы за простым
  интерфейсом.
- **Поверхностный модуль** — модуль, где вызывающий код должен знать почти
  столько же деталей, сколько есть внутри самого модуля.
- **Локальность** — свойство, при котором правило, ошибка или изменение живёт в
  одном месте, а не размазано по нескольким файлам.
- **Проверка удалением** — мысленная проверка: что будет, если удалить модуль.
  Если сложность исчезнет, модуль был лишним. Если та же сложность появится в
  нескольких местах, модуль действительно нужен.

## Общий вывод

Основная структура кода всё ещё хорошая:

`journal <- state <- mechanics <- phases <- engine`

Рядом с ней находятся `loaders` и `routing`. `gbp/model/flows.py` и
`gbp/routing.Routes` остаются хорошими модулями: у них небольшой интерфейс, ими
пользуются многие места, и детали конкретного режима не протекают наружу.

Главные проблемы сейчас находятся в `app/`:

- построитель артефактов заново считает часть данных из журнала;
- порядок запуска сценария вручную записан в двух местах;
- схема файлов запуска (`data/runs/<run_name>/`) централизована только
  частично.

## Решения, которые не нужно пересматривать

Эти решения уже приняты в прошлом обзоре или в `Notations.md`.

1. Ячейки `notebooks/test_pipeline.ipynb` принадлежат пользователю. Любое
   изменение ноутбука должно вписываться в текущие ячейки.
2. Таблицы ресурсов зарезервированы (`Notations.md` §5b), хотя грузовики сейчас
   не работают в базовом воспроизведении.
3. Исторический загрузчик вычисляет `step_id`, а симулятор проставляет его сам.
   Это описано в `Notations.md` §0.1. Эти две ветки не нужно объединять.
4. Широкий журнал потоков остаётся. `get_flows_wide` нужен как одна таблица для
   чтения результатов глазами. Ниже есть пункт про второе, параллельное
   расширение журнала. Это не предложение удалить `get_flows_wide`.
5. Два способа считать inventory сделаны намеренно: живое состояние обновляется
   по шагам, а проверка пересчитывает его из журнала. Инвариант I3 нужен, чтобы
   ловить расхождения между ними.
6. При перенаправлении соседние станции по-прежнему ранжируются через
   евклидово расстояние (`neighbor_distance_sq`) в обоих режимах маршрутизации.
   В режиме `osrm` выбор станции идёт по прямому расстоянию, а время и цена
   плеча считаются по дорожной сети. Это решение зафиксировано. Пересматривать
   его стоит только если сценарии с перенаправлениями станут рабочими
   сценариями, а не проверками на крайние случаи.
7. `Notations.md` — словарь проекта. Новое имя в коде должно использовать уже
   существующий термин из словаря. Если термина нет, сначала нужно добавить его
   в `Notations.md`.

## Предложение 1 — `build_panel` заново считает данные из журнала

> **Статус: реализовано 2026-07-04.** Выбран второй вариант решения: в
> `flows.py` добавлены read-model-функции `flows_to_redirects` и
> `flows_to_losses(flows, reason)` (термины `redirects` и `losses` добавлены в
> `Notations.md` §9). `build_panel` теперь вызывает пять готовых функций
> `flows_to_*`, а `check_demand_split` использует `flows_to_losses` вместо
> своей группировки.

**Файлы:** `app/artifacts.py:94-108`, `gbp/model/flows.py:584-619`
(`flows_to_departures`, `flows_to_arrivals`), `gbp/model/flows.py:1106-1112`
(`check_demand_split`).

**Проблема.** `build_panel` сам строит колонки `departed` и `arrived`:

```python
counts: dict[str, tuple[pd.Series, str]] = {
    "departed": (is_user_departure(flows), "source_id"),
    "arrived": (is_docking(flows), "realized_target_id"),
    ...
}
```

После этого там повторяется та же схема `groupby` → `sum` → `rename`, которая
уже есть в `flows_to_departures` и `flows_to_arrivals`. Эти функции
экспортируются из `gbp.model` и уже считаются единым местом, где определены
такие агрегаты.

Для строки `lost_demand` есть ещё одно повторение: группировка в
`app/artifacts.py` дублирует часть логики из `check_demand_split`.

В итоге правило «как считать отправления» живёт сразу в нескольких местах.
Если это правило изменится, легко обновить одно место и забыть другое.

**Решение.** `build_panel` должен вызывать готовые функции `flows_to_*` и
присоединять их результат к сетке inventory. Внутри `build_panel` можно оставить
только `redirected` и `lost_dock_full`, потому что для них пока нет отдельных
функций в `flows.py`. Другой вариант — сначала добавить такие функции в
`flows.py`.

**Польза.** Если появится новый тип события, который двигает inventory,
изменение нужно будет сделать в одном месте. `panel` и журнал будут совпадать
по правилу, а не потому что разработчик аккуратно повторил код. Проверка
сохранения значений по колонкам (`artifacts.py:110-113`) останется защитой.

## Предложение 2 — порядок запуска сценария записан вручную в двух местах

> **Статус: реализовано 2026-07-04.** Порядок «sizing → запуск → проверка
> инвариантов» теперь живёт в одной функции `run_sized_scenario` в новом модуле
> `gbp/consumers/simulator/scenario.py`; там же `canonical_phases` и результат
> `ScenarioRun` (термины `canonical phases` и `sized run` добавлены в
> `Notations.md` §11). Runner и ячейка 4 ноутбука вызывают эту функцию.
> `graph_data` при запуске больше не изменяется: прогон идёт на копии с
> подобранным состоянием, и подобранные таблицы возвращаются в результате.
> Список трёх фаз определён в одном месте; `tests/scenarios.py` импортирует его
> оттуда. Прямые тесты — `tests/test_scenario.py`.

**Файлы:** `app/runner.py:136-174` (`run_scenario`),
`notebooks/test_pipeline.ipynb` cell 4, `app/runner.py:38-40`
(`canonical_phases`), `tests/scenarios.py:131-137`,
`app/views/run_scenario.py:17-21`.

**Проблема.** Один и тот же порядок действий записан вручную в `run_scenario` и
в ячейке 4 ноутбука:

конфигурация размера состояния → `size_state_for_demand` → запись новых
`initial_inventory_df` и `facilities_capacities_df` в `graph_data` →
конфигурация запуска → `Environment` → `run()` → журнал.

Эти две копии уже немного отличаются. Ноутбук привязывает результат обратно
через `attach_simulation`, а runner читает `env.simulated_flows_df` напрямую.

Порядок шагов важен. Если создать `Environment` до того, как в `graph_data`
попадёт состояние после `size_state_for_demand`, результат будет выглядеть
правдоподобно, но будет неправильным. Сейчас такой порядок нигде явно не
защищён.

Есть ещё две проблемы:

- `run_scenario` меняет общий кэшированный объект. В
  `app/views/run_scenario.py` `graph_data` хранится через `st.cache_resource`,
  а `runner.py:143-145` меняет его на каждом запуске. Сейчас это работает
  только потому, что каждый запуск сначала заново делает sizing. Это неявное
  правило без проверки.
- Список трёх фаз базового сценария скопирован три раза: в `runner.py`,
  `tests/scenarios.py` и в ячейке `phases_canonical` ноутбука.

**Решение.** Нужна одна функция уровня `gbp`: «запустить сценарий после
sizing». На вход она получает `graph_data`, параметры sizing и параметры
запуска. На выходе даёт финальный журнал и, если нужно, таблицы после sizing.

Runner и ноутбук должны вызывать эту функцию. Состояние после sizing лучше
передавать как локальные значения, а не записывать обратно в общий `graph_data`.
При этом нужно сохранить правило: изменения ноутбука должны вписаться в
существующие ячейки.

**Польза.** Порядок запуска будет описан в одной функции. Его можно будет
напрямую тестировать. Сейчас у `app/runner.py` нет прямых тестов. Интерфейс
«запустить базовый сценарий» станет одним вызовом вместо цепочки ручных шагов.

## Предложение 3 — views считают то, что должен считать построитель артефактов

> **Статус: реализовано 2026-07-04.** Плитки уровня «Whole-run total» на
> страницах Costs и Distance & duration читают `meta["totals"]`
> (`cost`, `distance_km`, `mean_duration_periods`) вместо повторного расчёта из
> `flow_totals`. `build_arcs` записывает координаты концов дуги
> (`source_lat`, `source_lng`, `target_lat`, `target_lng`) в `arcs.parquet`;
> карта поездок больше не присоединяет таблицу станций при отрисовке. Сводка
> «All types» определена в одном месте — `ui_shared.panel_commodity_slice`;
> `panel_slice`, `_facility_rows` и раскрывающийся блок страницы Single facility
> вызывают его.

**Файлы:** `app/views/costs.py:22-23`, `app/views/distance_duration.py:31-47`,
`app/views/trips_map.py:40-55`, `app/ui_shared.py:216`,
`app/views/facility_detail.py:33`, `app/views/facility_detail.py:96-99`.

**Проблема.** В UI есть расчёты, которые можно сделать заранее в
`app/artifacts.py`:

- В `costs.py` и `distance_duration.py` плитки заново суммируют `flow_totals`.
  Но `build_totals` уже записывает те же числа за весь запуск в `meta.json`.
- `trips_map._arc_rows` во время отрисовки присоединяет к дугам координаты
  `lat` и `lng` из таблицы станций. Эти координаты не зависят от выбора
  пользователя в интерфейсе, значит их можно записать заранее.
- Сводка по всем типам велосипедов (`All types`) написана в трёх местах:
  `ui_shared.panel_slice`, `facility_detail._facility_rows` и прямо в
  `facility_detail.py:96-99`.

При этом обычные действия UI остаются нормальными: выбрать период, станцию или
уровень агрегации можно во view. Проблема только в тех расчётах, которые не
зависят от действий пользователя.

**Решение.** Плитки должны читать `meta["totals"]`, как уже делает `kpi_row`.
`build_arcs` должен сохранять координаты концов дуги в `arcs.parquet`:
`source_lat`, `source_lng`, `target_lat`, `target_lng`.

Сводку `All types` нужно вынести в один общий helper или хранить такой уровень
агрегации прямо в `panel`.

**Польза.** UI снова будет только читать готовые артефакты и фильтровать их по
выбору пользователя. У каждого числа за весь запуск будет одно место, где оно
считается.

## Предложение 4 — список `PANEL_VALUES` связан с четырьмя ручными списками

> **Статус: реализовано 2026-07-04.** В `app/artifacts.py` появилась одна
> таблица описания метрик: dataclass `Metric` (имя колонки, полная подпись,
> короткая подпись, единица, признаки `panel_value` / `panel_total` / `kpi` /
> `more_is_worse`) и список `METRICS` (термин `metric` добавлен в
> `Notations.md` §12). Из него строятся `PANEL_VALUES`, панельная часть
> `build_totals`, словари `METRIC_LABELS` / `METRIC_SHORT` и плитки KPI
> (`kpi_row`); ручной список `_KPI_ITEMS` удалён. Тест
> `test_every_kpi_metric_has_a_total` проверяет, что у каждой KPI-метрики есть
> значение в `totals`.

**Файлы:** `app/artifacts.py:34` (`PANEL_VALUES`), `app/artifacts.py:273-274`
(список имён в `build_totals`), `app/ui_shared.py:29-38` (`METRIC_LABELS`),
`app/ui_shared.py:40-49` (`METRIC_SHORT`), `app/ui_shared.py:170-179`
(`_KPI_ITEMS`).

**Проблема.** Чтобы добавить одну колонку значений в `panel.parquet`, нужно
изменить примерно пять мест. Все эти места связаны только вручную.

Если забыть одно место, ошибка может пройти незаметно. Например, новая метрика
появится в выборе метрики на карте станций без подписи или не попадёт в KPI и
в totals в `meta.json`.

**Решение.** Нужна одна таблица описания метрик. Для каждой метрики в ней
должны быть:

- имя колонки;
- полная подпись;
- короткая подпись;
- признак, входит ли метрика в KPI;
- признак, входит ли метрика в totals.

Тогда `PANEL_VALUES`, словари подписей, `_KPI_ITEMS` и `build_totals` можно
строить из этой таблицы.

**Польза.** Схема `panel` будет меняться в одном месте. Нельзя будет добавить
метрику и случайно забыть её подпись или сумму за весь запуск.

## Предложение 5 — схема `meta.json` описана дважды, а путь с `t0` не проверяется

> **Статус: реализовано 2026-07-04.** Контракт `meta.json` теперь строит одна
> функция `artifacts.build_meta`; её вызывают и runner, и тестовая фикстура
> `_save_run`, поэтому smoke-тесты страниц идут по той же ветке, что и рабочий
> код (`t0` и `routing_mode` всегда записаны). Ветки «`t0` отсутствует» удалены:
> `period_start_time` больше не возвращает `None`, `level_line_chart` и страница
> Single facility всегда показывают ось времени, `routing_mode` читается без
> `.get`. Прямой тест — `test_meta_carries_t0_and_the_run_parameters`. Старые
> артефакты, сохранённые без `t0`, страницы больше не откроют — их нужно
> прогнать заново.

**Файлы:** `app/runner.py:175-188`, `tests/test_app_artifacts.py:44-54`,
`app/ui_shared.py:132-139` (`period_start_time`),
`app/ui_shared.py:351-352`, `app/views/facility_detail.py:47-51`.

**Проблема.** Runner всегда записывает `t0` и `routing_mode` в `meta.json`.
Тестовая фикстура вручную строит `meta` без этих полей. Получаются две версии
одного контракта папки запуска, и они отличаются.

Из-за этого smoke-тесты страниц проверяют только ветку «`t0` отсутствует».
Основная ветка новой функции времени по часам, где `t0` есть, остаётся без
теста. Ветки fallback для случая без `t0` живут только из-за тестовой фикстуры.
Канонический pipeline такие артефакты уже не создаёт.

**Решение.** Нужна одна функция построения `meta` в `app/artifacts.py`. Её
должны вызывать и runner, и тестовая фикстура.

После этого нужно решить, оставлять ли ветки «`t0` отсутствует». По правилу
минимума для канонического сценария их лучше удалить.

**Польза.** Контракт папки запуска будет описан один раз. Тесты начнут
проверять тот же путь, который использует рабочий код. Новая функция времени
по часам получит покрытие тестами.

## Предложение 6 — расширение журнала реализовано дважды, а длительность имеет четыре имени

> **Статус: реализовано 2026-07-04.** В model layer добавлена одна функция
> расширения журнала — `flows_with_measures` (термин `measures` добавлен в
> `Notations.md` §6.1): она даёт каждому событию длительности, расстояния и
> деньги (`rate`, `elapsed_periods`, `cost` через `flows_with_costs`). Её
> вызывают и `get_flows_wide`, и `build_run_tables` — `flows.parquet` теперь
> тоже несёт полный набор measure-колонок. Каноническое имя длительности —
> `duration_periods` (строка добавлена в `Notations.md` §6): в широком журнале
> это `planned_duration_periods` / `realized_duration_periods` (старые
> `planned_duration` / `realized_duration` удалены); `elapsed_periods` остаётся
> отдельным термином §6 — «время в пути на момент события». Тест —
> `test_flows_table_carries_the_measures`.

**Файлы:** `gbp/loaders/dataloader_graph.py:671-746` (`get_flows_wide`),
`app/artifacts.py:119-165` (`build_arcs`), `app/artifacts.py:227`
(`build_flow_totals`), `gbp/model/flows.py:917` (`flows_with_costs`).

**Проблема.** Операция «добавить к журналу атрибуты станций, расстояние,
длительность и стоимость» написана в двух местах:

- в `get_flows_wide`;
- в построителях артефактов в `app/artifacts.py`.

Правило расчёта расстояния уже общее: оно идёт через `Routes` и
`flows_with_costs`. Но само расширение журнала всё ещё сделано параллельным
кодом. Чтобы понять, как выглядит журнал с ценой, нужно читать оба места.

Ещё одна проблема — имена длительности. Один и тот же смысл записан под
разными именами в разных модулях:

- `elapsed_periods`;
- `planned_duration`;
- `realized_duration`;
- `duration_periods`.

По правилам `Notations.md` это расхождение словаря.

Важно: `get_flows_wide` остаётся. Проблема не в нём, а во второй реализации
похожего расширения и в разных именах для длительности.

**Решение.** Нужна одна функция расширения журнала в model layer. Её должны
вызывать и ноутбук для широкого журнала, и построители артефактов.

Также нужно выбрать одно каноническое имя для длительности. Сначала добавить
его в `Notations.md`, потом использовать в коде.

**Польза.** Вид журнала с ценой будет понятен из одного места. Словарь и код
перестанут расходиться.

## Предложение 7 — в формуле стоимости есть неявное значение по умолчанию

> **Статус: реализовано 2026-07-04.** `period_len` в `flows_with_costs` стал
> обязательным параметром (в `flows_with_measures` он был обязательным с самого
> начала). Тесты передают его явно; демонстрационная ячейка ноутбука передаёт
> `pd.Timedelta(hours=1)` с комментарием, почему параметр обязателен. Итоговая
> стоимость прогона не изменилась (20123.0).

**Файлы:** `gbp/model/flows.py:876-878`.

**Проблема.** В `flows_with_costs` у `period_len` есть значение по умолчанию:
один час. Если вызывающий код забудет передать реальную длину периода,
стоимость будет рассчитана неправильно, но ошибки не будет.

В демонстрационной ячейке ноутбука это значение по умолчанию уже используется.

**Решение.** Сделать `period_len` обязательным параметром. Другой вариант —
передавать один небольшой объект времени, который хранит и `period_len`, и
`t0`.

**Польза.** Ошибка настройки станет невозможной: код не запустится без явной
длины периода. Цена изменения небольшая: нужно передавать ещё один аргумент в
местах вызова.

## Предложение 8 — в коде есть неиспользуемые части

> **Статус: реализовано 2026-07-04.** Удалены `load_gbfs_raw_df`,
> `get_stations_capacities`, `get_initial_inventory_df`, `slice_flows_wide` и
> `Schedule` (фазы теперь выполняются каждый период без проверки расписания).
> `RawModelData` больше не принимает `gbfs_base` и не ходит в сеть; параметр
> убран из `app/runner.py` (включая флаг `--gbfs-base`), со страницы Run и из
> ячейки конфигурации ноутбука. Прочие ноутбуки (`check_pipeline`, `flat_env`,
> `build_wild_inventory`) всё ещё передают `gbfs_base` — они вне канонического
> сценария и не менялись.

**Файлы:** `gbp/loaders/dataloader_raw.py:238-245`,
`gbp/loaders/dataloader_raw.py:78-86` (`get_stations_capacities`),
`gbp/loaders/dataloader_raw.py:123-157` (`get_initial_inventory_df`),
`gbp/loaders/dataloader_graph.py:749-789` (`slice_flows_wide`),
`gbp/consumers/simulator/state.py:72-85` (`Schedule`).

**Проблема.**

- `load_gbfs_raw_df` делает сетевой запрос к live GBFS при каждом создании
  `RawModelData`. Но дальше `gbfs_raw_df` никто не использует: загрузка
  capacity из GBFS закомментирована и заменена константой 100, а
  `get_initial_inventory_df` нигде не вызывается.
- `slice_flows_wide` нигде не вызывается в `gbp/`, `app/`, `tests/` и ноутбуке.
  Его соседняя функция `get_flows_wide` используется и должна остаться.
- `Schedule` сейчас не нужен. Ни одна фаза не создаётся с нестандартным
  расписанием. Если удалить `Schedule` и вызывать каждую фазу каждый период,
  поведение не изменится. Его интерфейс (`every_n`, `should_run`, `every`)
  почти такой же маленький, как сама реализация (`period_id % every_n == 0`).

**Решение.** Убрать GBFS-запрос из пути по умолчанию или включать его только в
режиме, где он действительно нужен. Удалить неиспользуемые GBFS helpers,
`slice_flows_wide` и `Schedule`.

Перед удалением нужно проверить единственное упоминание `gbfs` в ноутбуке:
это конфигурационная ячейка, а ячейки ноутбука принадлежат пользователю.

**Польза.** Каждый запуск перестанет зависеть от сети без необходимости. Код
лучше совпадёт с текущей фазой проекта: оставить только то, что нужно
каноническому сценарию.

## Заметки по тестам

- У `app/runner.py`, `app/main.py` и `app/ui_shared.py` нет прямых тестов.
  Тесты страниц сейчас в основном проверяют, что страница открывается без
  исключения. Они также проходят только ветку «`t0` отсутствует» из предложения
  5.
- Построители артефактов тестируются напрямую и через запись-чтение папки
  запуска (`tests/test_app_artifacts.py`). Контракт папки запуска защищён одним
  главным тестом: `test_save_and_load_round_trip`.
- Слой подготовки данных не проверяется offline: `ResolvedModelData.__init__`,
  `dataloader_raw.py`, `get_periods_df`, `get_historical_flows_df` и
  `get_trip_speed_km_per_period`. В `tests/scenarios.build_resolved` вручную
  собирается `SimpleNamespace`, поэтому арифметика загрузчиков реально
  выполняется только в ноутбуке и runner.
- `save_run` записывает `meta.json` последним. Поэтому `list_runs` не показывает
  недописанную папку запуска. Это настоящее правило, но отдельного теста на
  него нет.
- Дублирование в `tests/invariants.py` намеренное: `move_id == event_id // 2`
  и `LEGAL_FLOW_SHAPE` являются независимыми проверками. Это описано в их
  docstrings. Это не расхождение, а осознанная проверка.
