# Гайд по разработке: от нуля до domain-agnostic платформы

> Написан по итогам разбора шести месяцев разработки (папка `retro/`).
> Парный файл к `working_rules.md`: тот — про то, как не сорваться,
> этот — про то, куда идти. Читать оба перед стартом новой фазы.

---

## 1. Главный принцип

**Платформа не проектируется — она выращивается из работающих доменов.**

Порядок всегда такой: сначала один конкретный домен доводится до конца,
платформа извлекается из него в предпоследней фазе, когда появляется
второй домен.

Это не мнение, а измеренный факт из ретро:

- SPEC.md «универсальной платформы», написанный в день 0, прожил 54 дня и умер.
- Ядро, придуманное до рабочего сценария, переписывалось трижды
  (graph → core → model), −90 тысяч строк в двух эпохах сносов.
- Реальное разделение на `gbp` и `domains/citybike` заняло 16 коммитов
  и две недели — когда конкретная система уже работала.

Обобщение поверх работающего конкретного — дёшево.
Обобщение заранее — это и есть те 90 тысяч снесённых строк.

### Что можно делать с будущим

Принцип запрещает не **думать** вперёд, а **строить** вперёд.
Три уровня, по цене ошибки:

| уровень | цена сегодня / цена ошибки | вердикт |
|---|---|---|
| думать и записывать | ноль / ноль | всегда: карта фаз, `Notations.md`, `platform_ideas.md` |
| держать двери открытыми | ноль / ноль | да — что такое дверь, см. ниже |
| строить механизм под будущее | дорого / снос | только при втором потребителе: реестры, плагины, параметры «на вырост» |

**Дверь** — это выбор между двумя вариантами, которые сегодня стоят
одинаково, но один потом помешает изменению, а другой — нет.
Держать дверь открытой = выбрать второй.

Пример 1 — имя колонки в таблице инвентаря:

```
              сегодня      когда появились грузовики
bike_id       0 усилий     переименование по всему коду, тестам, докам
commodity_id  0 усилий     0 усилий
```

Цена сегодня одинаковая, цена завтра разная → выбираешь `commodity_id`.
Ты ничего не построил — просто выбрал слово.

Пример 2 — откуда движок берёт спрос. Вариант А: движок сам читает
CSV внутри себя. Вариант Б: движок принимает таблицу аргументом —
`run(demand_df, ...)`. Кода поровну. Когда позже пришёл ML-прогноз:
при А пришлось бы переписывать движок, при Б — передать другую таблицу.

Проверка «дверь или стройка»: **покажи пальцем на код, добавленный
ради будущего.** Дверь — показать не на что: лишнего кода нет,
ты выбрал слово или форму аргумента. Механизм — есть на что:
класс-протокол, реестр, параметр, который сегодня никто не передаёт.

Страховка от «потом не переделаешь» — не предвидение, а четыре свойства,
которые держатся в каждой фазе: зелёные тесты-сценарии; данные на швах
(таблицы, артефакты), а не вызовы вглубь друг друга; один источник
истины; понимание догнало код. Пока они держатся, любая переделка
стоит неделю-две — июльское разделение слоёв это доказало.
Спекулятивная абстракция страхует хуже: AttributeRegistry строился
«чтобы потом не переделывать» — будущее пришло другим, снесён.

Формула: **думай хоть на десять шагов — руками строй только текущий
и не заколачивай бесплатных дверей.**

## 2. Карта фаз

```
Фаза 0  Данные и словарь            ~2 нед   якорь: рассказать задачу человеку
Фаза 1  Реплей истории              ~6 нед   якорь: демо «месяц истории сходится»
Фаза 2  Сценарии «а что если» + UI  ~2 нед   якорь: демо в браузере конкретному человеку
Фаза 3  Ребалансировка              ~4 нед   якорь: отчёт «+Y% спроса при N грузовиках»
Фаза 4  Прогноз спроса (ML)         ~6 нед   якорь: отчёт с метриками двух уровней
Фаза 5  Второй домен → gbp          ~4 нед   якорь: один движок гоняет два домена
Фаза 6  Витрина                     ~2 нед   якорь: собеседование / публикация
```

Фаза начинается только при двух условиях:

1. Есть **внешний якорь** — дата, демо конкретному человеку, собеседование.
2. Есть **«готово»-предложение** — одно, проверяемое, записанное до старта.
   Не «чистая архитектура», а «команда X прогоняется и даёт Y».

### Фаза 0 — Данные и словарь

EDA на реальных данных в одном ноутбуке. Никакого кода в пакет.

- **Готово:** один экран текста — какую задачу решаем, на каких данных —
  плюс «готово»-предложение фазы 1.
- **Появляется:** `Notations.md` — с первого дня. Не спека, а словарь:
  сущности, обозначения, инварианты. Единственный документ, который
  в реальной истории пережил всё (108 правок).
- **Не делать:** SPEC на 1000 строк, дерево docs/, слово «платформа».

### Фаза 1 — Реплей истории

Вертикальный срез: прогнать месяц реальных данных через симулятор
и доказать сходимость баланса.

- **Готово:** «`python -m citybike.replay --month 202601` прогоняет месяц
  и печатает отчёт о сохранении инвентаря».
- **Появляется:** пакет `citybike/` (не `gbp/`!), плоская структура.
  Журнал событий как единственный источник истины.
  Тесты с первого дня — в выжившем формате: игрушечные сценарии
  («один велосипед, две станции, редирект») как `scenarios.md`
  + `test_scenarios.py`. Именно они делают будущие переделки дешёвыми.
- **Не делать:** пирамиду tests/unit + integration + fixtures
  (в реальной истории снесена целиком). Абстракции «на вырост».
  Мысли «а вот это по идее domain-agnostic» — одной строкой
  в `platform_ideas.md`, не в код.

**Откуда берётся модель данных.** Она не проектируется отдельным этапом —
она выпадает из проверки. «Готово» требует «реплей корректен» — значит,
надо записать формулой, что такое корректен: начальный остаток
+ приехавшие − уехавшие = конечный остаток на каждой станции.
Слово «инвентарь» рождается в этой формуле — как имя величины, которую
проверка требует сохранять. Проверку сначала считаешь руками в ноутбуке,
до всякого симулятора. Баланс не сойдётся — в поездках не видно ночных
перевозок грузовиками — и каждое такое сопротивление данных добавляет
кусок модели (потерянный спрос, редирект, ёмкость доков) и слово
в `Notations.md`. Ретро подтверждает: выжило ровно то, чего требовала
проверка (журнал, проекция инвентаря, инварианты); умерло
спроектированное умозрительно (AttributeRegistry, роли, transformations).

**Как растёт структура папок.** Не сессией проектирования. Старт —
плоский минимум: `load.py`, `model.py`, `engine.py`, `journal.py`,
`checks.py`. Дальше два локальных правила вместо плана: файл делится,
когда болит (перевалил за ~500 строк или появились две несвязанные
причины его менять); папка появляется, когда три файла образуют
очевидную группу. Пустых папок «на будущее» не бывает. Имена — из
`Notations.md`, не из паттернов (никаких managers, factories).
Код рождается в ноутбуке и переезжает в пакет, когда стабилизировался:
так появилось выжившее ядро — `engine.py` и `state.py` жили
в `notebooks/` и переехали в пакет 5 июня. Настоящих архитектурных
решений в фазе одно-два («журнал — единственный источник истины,
остальное — проекции») — вот только их проектировать дважды на бумаге.

### Фаза 2 — Сценарии «а что если» + минимальный UI

Дешёвое вмешательство — множитель спроса ×k — и машинерия сравнения прогонов.

- **Готово:** «в браузере запускаются и сравниваются два сценария».
- **Появляется:** сохранённые артефакты прогона и минимальный Streamlit
  поверх них — по правилу одной боли: результаты стало больно
  смотреть в ноутбуке.
- **Не делать:** ребалансировку (следующая фаза), FastAPI
  (второго пользователя нет), Docker, деплой-планы.

### Фаза 3 — Ребалансировка

Первое умное вмешательство: грузовики ночью перевозят велосипеды.
Оно приходит в готовую машинерию сравнения из фазы 2 и становится
ещё одной ручкой сценария.

- **Готово:** «ребалансировка против бейзлайна на одинаковой физической
  картине даёт +Y% удовлетворённого спроса при N грузовиках».
- **Первым появляется протокол эксперимента** — один экран, до кода:
  что фиксировано между сценариями (initial_inventory и ёмкости —
  sizing-прогоном по историческому спросу), что варьируется
  (вкл/выкл, число грузовиков), какая метрика. «Готово»-предложение
  обязано называть протокол, а не только фичу.
- Каждая тонкость «честности», всплывшая при написании протокола, —
  один короткий decision-файл (формат, который в реальной истории выжил:
  `docs/decisions/sizing-run.md`). И каждую тонкость прогнать
  на игрушечном примере с настоящими числами: три станции,
  два периода, табличка руками.
- **Не делать:** доработки UI сверх новой ручки сценария.

### Фаза 4 — Прогноз спроса (ML)

ML внутри домена: таблица признаков, бэктест, прогноз, двухуровневая оценка
(метрики модели + прогон симулятора на прогнозе против истории).

- **Готово:** «`--demand-source forecast` прогоняет симуляцию на прогнозе
  чемпиона; отчёт: модель X даёт MAE Y, симулятор на её прогнозе
  отклоняется от истории на Z%».
- **Появляется:** MLflow — когда моделей стало больше одной
  (сегодняшняя боль, не карго-культ).
- **Держать:** прогноз заменяет **только** спрос; начальный инвентарь
  и ёмкости — исторические. Такие решения — короткие decision-файлы.
- **Не делать:** облачный MLOps, автодообучение, дрифт-мониторинг
  без живого потребителя.

**Интеграция через данные, а не через код.** Симулятор с фазы 1
потребляет спрос как таблицу (facility, period, quantity) и не знает,
откуда она взялась; прогноз — просто ещё один производитель той же
таблицы. Порядок работ: обучение и бэктест офлайн, движок не трогается →
прогноз сохраняется как артефакт в схеме исторического спроса →
одна функция на шве загрузчика `apply_forecast(data, forecast)` →
в конфиге прогона `demand_source: history | forecast`; ручка в UI
после этого тривиальна. Проверка шва: если для встраивания модели
пришлось лезть в `engine.py` — шов выбран неправильно, остановись.

### Фаза 5 — Второй домен → рождение gbp

Единственно правильный момент для платформы. Механика — в разделе 4.

- **Готово:** «один движок прогоняет citybike и второй домен;
  `grep -rn "domains\." gbp/` пуст».

### Фаза 6 — Витрина

Сайт документации, quickstart, портфолио — один раз, в конце,
по замороженной системе. До этой фазы во всём репозитории живут
ровно три документа (раздел 7).

## 3. Устройство любой фазы изнутри

Подфазы везде одинаковые — голова всегда знает, в каком такте находится:

```
разведка → план-тикеты → [порция → прогон]* → стабилизация → демо + ретро
 1-2 дня     полдня        основное время        1-2 дня        вечер
```

**Разведка.** Читаю, копаюсь в ноутбуке, ничего не пишу в пакет.
Выход — «готово»-предложение, список тикетов, а для фазы-эксперимента —
протокол сравнения на один экран.

**План.** Тикеты маленькие (≤ полдня каждый), лежат в `.scratch/`,
удаляются по выполнении. Дизайн-док длиннее одного экрана
до работающего кода — красный флаг.

**Порция — главный такт против разрыва «код быстрее понимания».**
2–3 тикета Claude подряд, не больше. Потом обязательно: прогнать руками,
прочитать дифф, суметь объяснить его себе за 30 секунд.
Не могу объяснить — сначала «объясни», потом «давай».
После 22:00 — только мелочь, ничего архитектурного.

**Стабилизация.** Тесты зелёные, `Notations.md` догнал код,
мусор снесён осознанным коммитом: что сношу, почему, какой урок.

**Демо и ретро.** Показать якорному человеку. Полстраницы
в один append-only файл ретро. Разобрать wishlist: что всё ещё
волнует через месяц — настоящее, остальное было зудом.

**Заморозка.** Фаза заканчивается мержем в живой `main` и тегом
(`v0.1-replay`, `v0.2-scenarios`, `v0.3-rebalancing`, …).
Точка возврата + записанные уроки.

## 4. Фаза 5 подробно: форк → дифф → извлечение

Ни «с нуля», ни «выношу общее по ходу». Три такта:

```
А. Форк          скопировал citybike → второй домен, довёл до
                 первого прогона. Оригинал не трогаю.            ~1-2 нед
Б. Дифф-карта    сравнил две папки: что не тронуто / переписано /
                 поправлено местами. Проект разделения не
                 придуман, а измерен.                            ~1 день
В. Извлечение    по одному модулю за коммит уношу общее в gbp,
                 оба домена зелёные на каждом шаге.              ~1-2 нед
```

**Копия — это измерительный прибор.** Границу «общее/доменное»
не проектируют головой — её измеряют диффом двух работающих доменов.

### Такт А — форк

Второй домен: структура похожа, но хотя бы одно измерение другое
(пример: такси Нью-Йорка — есть поездки и спрос, но нет доков и грузовиков).

```bash
cp -r citybike/ taxi/
```

Правишь копию, пока один сценарий не прогонится конец-в-конец. Три правила:

- **Оригинал заморожен.** Ни одной правки, даже «мелкой попутной» —
  он твой зелёный эталон.
- **Копии разрешено быть уродливой.** Закомментировать, захардкодить — нормально.
  Цель такта — знание, не чистота.
- **Никаких «вынесу-ка сразу общее».** Кандидат на общее — строка
  в `platform_ideas.md`, едешь дальше.

Зуд от дублирования — нормален и дёшев: копия живёт две недели.
Неправильная абстракция до второго домена жила полгода
и стоила трёх переписываний ядра.

### Такт Б — дифф-карта

Днём, на свежую голову. Каждый файл — в одну из трёх колонок:

| колонка | что это значит | куда едет |
|---|---|---|
| не тронул ни строки | domain-agnostic, доказано делом | в `gbp/` |
| переписал целиком | доменное | остаётся в домене |
| поправил местами | **шов** — нужен параметр или протокол | скелет в `gbp/`, крючки — доменам |

Швов обычно два-три, не двадцать. Только для них имеет смысл
спроектировать интерфейс дважды на бумаге.

Итог такта — один экран: файлы по колонкам + «готово»-предложение такта В.

### Такт В — извлечение

1. Сначала лёгкое: колонка «не тронул» переезжает в `gbp/`,
   оба домена импортируют оттуда, копии удаляются.
   Один модуль = один коммит. После каждого — smoke-сценарии **обоих** доменов.
2. Потом швы: общий скелет + ровно те крючки, что нужны двум реальным
   доменам. Не три «на вырост».
3. Проверка границы: `grep -rn "domains\." gbp/` пуст.
4. Реестр доменов, оркестратор — только при живом потребителе.

### Почему не иначе

- **«С нуля»** — писать второй домен против воображаемого ядра =
  тот же дизайн платформы в голове, только сбоку.
- **«По ходу»** — обобщать, посмотрев на полтора домена: ломаешь
  зелёный эталон и держишь в голове две задачи сразу
  («заставить работать» и «спроектировать границу»).
  Расхождение картин в голове — главный источник сносов.

## 5. Если граница уже существует и не нравится

Типовая ситуация: гайд читается с уже написанным кодом — разделение
на ядро и домен есть, но сделано не по этому процессу, и список
претензий к границе растёт.

Правило то же: **пересборка границы — это такт В форка, а не его
предусловие.** Претензии к границе — представления автора о том,
что удобно пользователю, которого ещё не существует. Первым настоящим
пользователем ядра станешь ты сам, когда напишешь второй домен.
Пересборка до него — проектирование по воображению, за которым
неизбежно придёт вторая пересборка.

Порядок:

```
1. Полдня   претензии → гипотезы с проверками (boundary_hypotheses.md
            в .scratch/): не «фронт завязан на домен», а «страницы X, Y
            заработают на втором домене без правок, Z — нет»
2. ~2 нед   форк по такту А. Ядро и первый домен заморожены. Каждый
            лишний интерфейс на пути — строка в friction log, не правка
3. 1 день   дифф-карта + friction log против гипотез: что подтвердилось —
            в план такта В; что нет — зуд был ложный
4. ~2 нед   такт В = пересборка по фактам, оба домена зелёные
            на каждом коммите
```

Хорошие проверки для гипотез: список имён, реально импортированных
из ядра во второй домен (это измеренная поверхность интерфейса);
запуск сценария, написанный дважды — через текущие обёртки
и напрямую из движка с фазами: публичным становится тот вариант,
который объясним за 30 секунд.

До форка позволено только одно: снос мёртвого кода по правилу
«нет потребителя», осознанным коммитом. Удалять мёртвое — да,
перекраивать живые интерфейсы — нет. Поймал себя на «заодно поправлю
сигнатуру» — стоп, это уже такт В, ему рано.

---

## 6. Куда деваются переделки

Они не запрещаются — переносятся из реакции на дискомфорт
в запланированное окно:

1. **Архитектурное ревью — только на границе фаз**, максимум 3 пункта,
   чинящих конкретную боль. Пара «генератор + ревьюер» находит
   кандидатов бесконечно — границу ставит календарь, а не исчерпание списка.
2. **«Не умещается в голове» — триггер стабилизации, не сноса**:
   остановиться, догнать пониманием, синхронизировать код,
   доки и картину в голове через `Notations.md`.
3. **Обобщение отложено до второго потребителя** — главный источник
   переделок (переписывание ядра под воображаемую универсальность)
   просто не возникает.

## 7. Документы

До фазы 6 во всём репозитории живут ровно три документа:

| документ | зачем |
|---|---|
| `README.md` | как запустить |
| `Notations.md` | словарь + инварианты; правится, не пересоздаётся |
| `scenarios.md` | игрушечные сценарии = тесты |

Всё остальное — тикеты в `.scratch/` (умирают по выполнении),
короткие decision-файлы по мере принятия решений
и два append-only списка: `platform_ideas.md` (замыслы общего)
и wishlist переделок. Сайт и полная документация — один раз, в фазе 6,
по замороженной системе.

## 8. Если забуду всё остальное

Код появляется быстрее, чем понимание. Разрыв сокращают маленькие порции,
прогон руками, тесты и один словарь. А фазовая структура нужна, чтобы
у разрыва не было шести месяцев на накопление:
**он обнуляется на каждой границе фазы**.
