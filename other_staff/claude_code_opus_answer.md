# Как работает фаза `DockArrivals`

Разбор по коду `gbp/consumers/simulator/phases.py:72–201`. Вызываемые методы — из `mechanics.py`, `state.py` и `gbp/model/flows.py`.

## Что делает `DockArrivals` в одном предложении

Она берёт велосипеды, которые по плану прибывают в этом периоде, ставит их в свободные слоты доков на плановой станции, а те, что не влезли — перенаправляет на ближайшую станцию со свободным доком; если свободного дока нет нигде — записывает велосипед как потерянный. Всё это — один шаг («фаза») внутри периода.

Важный контекст: при точном повторе исторических данных доки никогда не переполняются, поэтому вся ветка с переполнением и перенаправлением просто не срабатывает. Она нужна только когда трафик выше исторического.

---

## Параметр `when`: почему докинг разбит на две фазы

Период состоит из четырёх фаз в таком порядке:

1. `DockArrivals(when="previous")` — пристегнуть велосипеды, которые **уехали в прошлых периодах** и прибывают сейчас.
2. `FormDeparturesPhase` — посчитать, сколько велосипедов уезжает в этом периоде.
3. `FormPotentialTripsPhase` — превратить эти счётчики в конкретные поездки.
4. `DockArrivals(when="same")` — пристегнуть велосипеды, которые **уехали и прибыли внутри этого же периода** (короткие поездки).

Один и тот же класс работает дважды, а `when` выбирает, какие прибытия он обрабатывает. Разница видна только в отборе `due` и в проставляемом `phase_rank` (об этом ниже). Конструктор просто проверяет допустимость значения и задаёт имя фазы:

```python
if when not in ("previous", "same"):
    raise ValueError(...)
self.name = f"dock_arrivals_{when}"
```

## Пошаговый разбор `execute`

### 1. Reads — отбор велосипедов, которые прибывают сейчас (строки 108–119)

```python
t = period.period_id
it = state.in_transit
arrived_now = it["planned_end_period"] == t
```

`in_transit` — это рабочий набор «уехали, но ещё не пристегнулись». Каждая строка — одна поездка (один велосипед) со своим `flow_id`. Отбираем те, у кого плановый период прибытия равен текущему `t`, и делим по времени старта:

- `when == "previous"` → `start_period < t` (уехали раньше),
- `when == "same"` → `start_period == t` (уехали в этом же периоде).

Если ничего не прибывает — сразу возвращаем `PhaseResult.empty(state)` (ничего не меняем).

`inventory_before` запоминает суммарный запас велосипедов до изменений — он нужен только для проверки в конце.

### 2. Mechanics — плановый докинг (строки 124–127)

```python
free = free_docks(inventory, capacities)
docked, overflow = dock_up_to_capacity(due, free)
new_flows = arrived_events(docked, t)
inventory = adjust_inventory(inventory, dock_deltas(docked))
```

Здесь работают четыре внутренних метода:

**`free_docks(inventory, capacities)`** → сколько свободных слотов у каждой станции. Обычные и электрические велосипеды делят одни и те же физические доки, поэтому занятость — это сумма запаса по всем типам: `capacity − occupied`, обрезано снизу нулём.

**`dock_up_to_capacity(due, free)`** → делит прибывающих на `(docked, overflow)`. Внутри каждой плановой станции первые `free` велосипедов (по порядку строк) пристёгиваются, остальные — переполнение. Реализовано без цикла на Python: через `groupby(...).cumcount()` считается позиция велосипеда в очереди к своей станции, и если позиция меньше числа свободных слотов — велосипед влез.

**`arrived_events(docked, t)`** → строит по одной записи `arrived` на каждый пристёгнутый велосипед. У такой записи `realized_target_id` равен плановой станции — велосипед доехал куда собирался.

**`adjust_inventory(inventory, dock_deltas(docked))`** → прибавляет +1 к запасу на каждой станции, где велосипед пристегнулся. `dock_deltas` группирует по станции и типу велосипеда и даёт `delta = +1` на каждое прибытие; `adjust_inventory` складывает эти дельты с текущим запасом.

### 3. Переполнение: перенаправление (строки 128–153)

Если `overflow` не пуст, вызывается главный метод этой ветки:

**`plan_overflow_redirect(inventory, capacities, geo, overflow)`** → решает, куда поедет каждый не влезший велосипед. Это **решение, а не изменение состояния**: метод возвращает две таблицы — `redirected` (с колонкой `realized_target_id` — куда велосипед в итоге пристегнулся) и `lost` (для кого свободного дока не нашлось нигде). Как он работает внутри:

- Работает **раундами**, а не по одному велосипеду. В каждом раунде: считает свободные доки на своей локальной копии запаса, находит для каждого ещё не пристёгнутого велосипеда ближайшую свободную станцию (`_nearest_free_station`), пристёгивает столько, сколько влезает (`cumcount` как выше), помечает их номером раунда `phase_round` и обновляет локальную копию запаса.
- Затем повторяет с оставшимися. Цикл кончается, когда не осталось велосипедов или нигде нет свободного дока.
- Локальная копия запаса `running` нужна, чтобы велосипеды из раунда 2 «видели» доки, уже занятые раундом 1. Она не покидает функцию.

**`_nearest_free_station(targets, free, geo)`** → для каждой плановой станции находит ближайшую **другую** станцию со свободным доком. Расстояние — квадрат евклидова по (`lat`, `lng`); для прототипа этого достаточно. Внутри строится декартово произведение «плановые станции × кандидаты», исключается сама с собой, сортируется по расстоянию и берётся ближайший.

Теперь ключевая модель — **перенаправление это две дуги** (строки 136–150):

```python
round_by_flow = redirected.set_index("flow_id")["phase_round"]
bounce = redirected_events(redirected, t)
bounce["phase_round"] = bounce["flow_id"].map(round_by_flow)
continuation = redirect_continuation_events(redirected, t)
continuation["phase_round"] = continuation["flow_id"].map(round_by_flow)
```

Велосипед планировал ехать A → B. Он уже уехал из A (запись `departed` создана раньше). Дальше:

- **`redirected_events` (отскок)** — велосипед доехал до B, но доки полны, поэтому «отскакивает» и **не** пристёгивается. Запись `redirected` (move 0, event 1), `realized_target_id = NA`. Это закрывает первую дугу A→B.
- **`redirect_continuation_events` (продолжение)** — велосипед едет дальше на C (найденную свободную станцию). Это вторая дуга: две записи в том же периоде — `departed` (move 1, event 2) из B и `arrived` (move 1, event 3) на C. Именно `arrived` на C пристёгивает велосипед — это единственный +1 всего перенаправления.

Важная тонкость про инвентарь: продолжение пристёгивает велосипед в **этой же фазе**, поэтому его move-1 `departed` **никогда не попадает в `in_transit`** — оно записано в журнал и тут же закрыто. И: move-1 `departed` — это **не** пользовательский отъезд (велосипед не стоял в доке B, B был полон), поэтому все читатели, считающие отъезды пользователей, фильтруют по `move_id == 0`.

Инвентарь меняется только на +1 на C:

```python
inventory = adjust_inventory(inventory, dock_deltas(redirected, "realized_target_id"))
```

Обрати внимание на второй аргумент `"realized_target_id"` — здесь велосипед пристегнулся не на плановой станции, а на той, куда его перенаправили.

### 4. Потерянные велосипеды (строки 154–162)

```python
new_flows = pd.concat([new_flows, lost_events(lost, t, "dock_full")], ...)
```

**`lost_events(lost, t, "dock_full")`** → по одной записи `lost` на велосипед, которому дока не нашлось нигде. Инвентарь **не меняется**: велосипед уже уехал со своей станции (там было −1 при `departed`) и теперь не пристёгивается никуда. Это чистый учёт — запись закрывает жизненный цикл поездки и делает потерю видимой в журнале.

### 5. `phase_rank` — порядок фаз внутри периода (строка 168)

```python
new_flows["phase_rank"] = DOCK_PREVIOUS_RANK if self.when == "previous" else DOCK_SAME_RANK
```

Ранги фиксированы: `DOCK_PREVIOUS_RANK = 0`, `PERIOD_OWN_RANK = 1`, `DOCK_SAME_RANK = 2`. Все события этой фазы (`arrived`, отскок, продолжение, `lost`) принадлежат одной фазе докинга, заданной параметром `when`. Ранг задаёт грубый порядок фаз: докинг «предыдущих» идёт до отъездов, докинг «своих» — после.

### 6. `step_id` — точный порядок изменений инвентаря (строки 176–187)

Это самое тонкое место. `phase_rank` разделяет фазы, но внутри одной `DockArrivals` изменения инвентаря происходят **по порядку**: сначала плановый докинг, потом раунд 1 перенаправления (он занимает доки, которые видит раунд 2), потом раунд 2 и так далее. Этот порядок нужно сохранить, чтобы позже `finalize_flows` смог восстановить историю в правильной последовательности.

```python
rounds = new_flows["phase_round"].fillna(0).astype("int64")  # если колонка есть
...
working = state
step_ids = pd.Series(0, index=new_flows.index, dtype="int64")
for r in sorted(rounds.unique()):
    sid, working = working.open_step()
    step_ids[rounds == r] = sid
new_flows["step_id"] = step_ids
```

- `phase_round` равен 0 для планового докинга (и для `lost`, который никуда не пристёгивается) и 1, 2, … для раундов перенаправления. `fillna(0)` ставит 0 записям `arrived` и `lost`, у которых этой колонки не было.
- Цикл проходит по различным раундам **по возрастанию** и на каждый открывает отдельный шаг.

**`open_step()`** (из `state.py`) выдаёт следующий номер из run-глобального счётчика `next_step_id` и возвращает новое состояние с увеличенным счётчиком. Номер берётся из счётчика, **а не из колонок событий**, поэтому два упорядоченных набора никогда не получат один `step_id` — даже если у них совпадают `(period_id, phase_rank, phase_round)`. Возрастающие `step_id` внутри фазы говорят: сначала применился плановый докинг, потом раунд 1, потом раунд 2.

Переменная `working` накапливает продвинутый счётчик — именно её (а не исходный `state`) используем дальше.

### 7. Writes (строки 191–192)

```python
in_transit = state.in_transit.drop(due.index)
new_state = working.with_inventory(inventory).with_in_transit(in_transit)
```

Пристёгнутые велосипеды убираются из `in_transit` (все `due`, независимо от того, пристегнулись они на плане, были перенаправлены или потеряны — они больше не в пути). `with_inventory` и `with_in_transit` возвращают **копии** состояния (dataclass `frozen=True`, состояние никогда не мутируется на месте). `working` несёт вперёд продвинутый счётчик шагов.

### 8. Проверки-инварианты (строки 197–200)

```python
assert len(docked) + n_redirected + n_lost == len(due), "due flows not conserved"
assert int(inventory["quantity"].sum()) - inventory_before == len(docked) + n_redirected, ...
```

- Первая: каждый прибывающий велосипед учтён ровно один раз — либо пристегнулся на плане, либо перенаправлен, либо потерян.
- Вторая: инвентарь вырос ровно на число реально пристёгнутых (`docked + redirected`). Потерянные велосипеды инвентарь не двигают.

Возвращается `PhaseResult(new_state, new_flows)`. Движок потом сам добавит `new_flows` в журнал через `state.append_flows`.

## Сводка внутренних методов

- **`free_docks`** — свободные слоты на станцию = вместимость − занятость (по сумме всех типов велосипедов).
- **`dock_up_to_capacity`** — делит прибывающих на «влезли» / «переполнение» через `cumcount`, без цикла.
- **`plan_overflow_redirect`** — раундами планирует, куда поедет каждый не влезший велосипед; возвращает решение, состояние не трогает.
- **`_nearest_free_station`** — ближайшая другая станция со свободным доком (квадрат евклидова расстояния).
- **`arrived_events` / `redirected_events` / `redirect_continuation_events` / `lost_events`** — строители записей журнала для четырёх исходов: пристегнулся, отскочил, доехал до запасной станции, потерян.
- **`adjust_inventory` + `dock_deltas`** — прибавляют +1 к запасу на станции докинга (по плановой или по перенаправленной колонке).
- **`open_step` / `with_inventory` / `with_in_transit`** — функциональные обновления неизменяемого состояния: выдать номер шага и заменить инвентарь / набор «в пути».
